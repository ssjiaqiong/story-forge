## 一、定位

一句话：**把一本小说，一键转换成一份可以直接开机的短剧文字拍摄本。**

```
小说（章节正文 + 人物 + 设定）
        ↓ 一键转换（AI 分五个阶段，每阶段可改可重做）
短剧项目
   ├─ 一句话卖点 / 短剧简介      ← 给平台招商、给观众看的
   ├─ 人物表（6~10 人）          ← 给选角、给演员看的
   ├─ 场景表                     ← 给制片、给美术看的
   ├─ 物品 / 道具表              ← 给道具组看的
   ├─ 剧集表（分集大纲）          ← 给导演、给平台审的
   └─ 分镜表（逐集逐场逐镜）      ← 给摄影、给剪辑看的
        ↓ 导出
Word / PDF / Markdown / 分镜 CSV
```

**它不是「小说摘要工具」。** 摘要保留信息，改编要**做取舍和重组**：小说里的心理描写必须变成台词或动作，20 个配角要合并成 8 个，跨 5 章的一条支线要压成一集。这是媒介转换，不是压缩。

三条设计原则：

1. **小说是源，短剧是派生物。** 单向引用，短剧库的编辑**不修改小说的任何数据**。小说改了不自动改短剧，提供显式的「重新同步」。
2. **先定骨架，再填血肉。** 人物、场景、道具这三张表是**全局字典**，后续所有分镜只能引用字典里的名字。这是防止「第 8 集突然冒出个没登记的角色」的唯一办法。
3. **分块重做，不整体重跑。** 第 12 集的分镜不满意，只重做第 12 集。整本重跑要几十次 AI 调用，代价太高，不能是唯一选项。

## 二、与书架的关系（明确边界）

| | 书架 / 小说工作台 | 短剧库 |
|---|---|---|
| 位置 | 一级菜单「书架」 | **新增一级菜单「短剧库」**，与书架并列 |
| 内容 | 章节正文、大纲、人物、设定、体检 | 短剧简介、人物表、场景表、道具表、剧集、分镜 |
| 数据方向 | 主数据 | 只读取小说，**从不回写** |
| 删除小说 | — | 短剧项目保留，标记「原著已删除」，仍可导出 |

**不做的事**：不在工作台里加「短剧」页签，不在书籍详情里挂短剧列表。两个模块通过 `novel_id` 关联，但界面互相独立——这样短剧库以后能接「非本平台小说」（手工导入大纲）而不用改结构。

> 技术实现上，一级菜单由路由 `meta: { title, icon, menu: true }` 驱动（见 `web/src/router/index.ts`），加一个路由就是加一个菜单，不需要改侧边栏组件。

## 三、短剧的行业结构（这决定了功能形状）

短剧不是「短的小说」，它有硬性的结构约束。这些约束必须写进提示词，否则 AI 会生成一个「分集的小说」，没法拍。

| 层级 | 约束 | 说明 |
|---|---|---|
| 短剧 | 竖屏 80~100 集 × 60~90 秒；或横屏精品 24 集 × 2 分钟 | 两种形态的节奏完全不同，配置时必须选 |
| 集 | 每集必须有：**前 3 秒钩子 → 冲突升级 → 一次反转 → 结尾悬念** | 缺钩子就没有完播率，缺悬念就没有下一集 |
| 场 | 单集 3~5 场 | 「同一地点 + 同一时间」为一场；一场戏不超过 40 秒 |
| 镜 | 单场 3~8 镜 | 每镜 3~8 秒；短剧平均 4 秒一个镜头 |
| 人物 | **6~10 人**（小说通常 20~30 人） | 必须做合并：把「三个不同部门的同事」合成「一个同事」 |
| 场景 | 8~15 个（小说通常 30+ 个地点） | 场景数是成本项，同一场戏能换地点就换 |
| 道具 | 5~10 个「有戏」的物品 | 只保留推动情节或标识身份的，其余删掉 |

按 24 集估算：24 集 × 4 场 × 5 镜 ≈ **480 个镜头**。这是分镜表的规模，也是必须分块生成的原因。

## 四、功能清单

### P0 · 主线（缺一项就交不出完整拍摄本）

| 编号 | 功能 | 说明 | 验收要点 |
|---|---|---|---|
| D-01 | 短剧项目 | 从小说创建：选小说 → 选章节范围（全本 / 第 X~Y 章）→ 配置参数 | 参数见下表；创建后进入流水线 |
| D-02 | 一键转换 | 五阶段流水线：故事提炼 → 人物 → 场景与道具 → 分集大纲 → 分集分镜 | 每阶段独立完成、独立可重做；前一阶段未完成时后一阶段禁用 |
| D-03 | 故事提炼 | 输出：一句话卖点（≤30 字）、短剧简介（150~300 字）、主线三段式（起 / 转折 / 结局）、题材标签 | 简介里不出现小说专有名词以外的生造词；字数在范围内 |
| D-04 | 人物表 | 从小说角色**映射**而非重造：姓名、身份、年龄、外貌、性格、核心动机、人物弧光、在短剧中的作用（主角/反派/工具人）；支持合并与新增 | 人数落在配置范围内；每个人都写明「为什么必须存在」 |
| D-05 | 场景表 | 场景名、地点、内外景、时间（日/夜/晨）、氛围、涉及人物、出现集数 | 场景数 ≤ 配置上限；同名场景不重复登记 |
| D-06 | 物品 / 道具表 | 名称、首次出现集、作用（推动情节/身份象征/关键线索）、是否需特写 | 每个道具必须挂到至少一集，否则不允许保留 |
| D-07 | 剧集表 | 集号、标题、时长、**前 3 秒钩子**、本集冲突、反转点、结尾悬念、对应小说章节 | 每集四个字段（钩子/冲突/反转/悬念）都不为空，空则标黄提示 |
| D-08 | 分镜表 | 逐集生成：集号、场号、镜号、景别、运镜、画面描述、台词、动作、时长 | 单集镜数与时长落在配置范围；台词字数与时长匹配（约 4 字/秒） |
| D-09 | 单块编辑与重做 | 每条记录可改；可「重做这一条」「重做这一集」「重做整块」；可**锁定**（锁定后重做不覆盖） | 重做只影响选中范围；锁定项在批量重做时跳过并提示 |
| D-10 | 进度与续跑 | 五阶段 + 分集逐个的进度；中途关闭页面任务继续；可暂停、可继续 | 服务重启后卡在 RUNNING 的任务标为可续跑，不丢已完成的集 |
| D-11 | 导出 | Word（完整拍摄本）/ Markdown / 分镜 CSV（可直接进 Excel） | Word 按「封面 → 简介 → 人物 → 场景 → 道具 → 剧集表 → 分镜表」章节排；CSV 一镜一行 |

**D-01 的配置项**（这些参数直接决定 AI 的输出结构，不能事后改）：

| 参数 | 选项 | 默认 |
|---|---|---|
| 形态 | 竖屏 80~100 集 × 60~90 秒 / 横屏 24 集 × 120 秒 | 竖屏 |
| 集数 | 12 / 24 / 60 / 80 / 100（按原著字数给建议值） | 24 |
| 单集时长 | 60 / 90 / 120 秒 | 90 秒 |
| 改编力度 | 忠于原著 / 适度合并 / 大幅重写 | 适度合并 |
| 题材 | 都市情感 / 悬疑 / 古装 / 玄幻 / 逆袭 / 家庭 | 从小说标签推断 |
| 人物上限 | 6 / 8 / 10 | 8 |
| 场景上限 | 8 / 12 / 15 | 12 |

### P1 · 好用（交出去之前要过的几道检查）

| 编号 | 功能 | 说明 |
|---|---|---|
| D-12 | 树形浏览 | 左侧「集 → 场 → 镜」三级树，右侧编辑选中节点，比一张大表好用 |
| D-13 | 引用一致性校验 | 分镜里出现的人物/场景/道具必须在字典表里，否则标红并给「加入字典 / 改成已有项」两个动作 |

### P2 · 进阶（有额外成本或依赖外部流程）

| 编号 | 功能 | 说明 |
|---|---|---|
| D-20 | 多套改编方案 | 同一本书出「甜宠向」和「悬疑向」两版，并排对比卖点与分集 |
| D-21 | 通告单导出 | 按场景聚合拍摄顺序（同场景的戏集中拍），输出拍摄计划表 |
| D-22 | 从大纲反向导入 | 不依赖本平台小说，手工贴一份大纲也能生成短剧 |
| D-23 | 与画面/视频打通 | 分镜的「画面描述」可直接送文生图或图生视频。**一期不做，已独立为二期视觉层设计**（`2026-11-10-短剧库-视觉层（视频生成与合成）.md`）；一期必须留好 `visual / duration_sec / speaker / scene_no` 四个字段，二期直接消费 |
| D-24 | 多人协作与评论 | 编剧 + 导演在同一份分镜上评论 |

### 明确不做（一期）

- 生成图片、配音、视频（一期范围外，**已独立为二期视觉层**）
- 剧本格式（好莱坞/国内电影剧本的标准格式），短剧不用那套
- 分镜画稿、故事板图片（二期用 AI 静帧替代，不做手绘稿）
- 自动投稿到短剧平台

## 五、数据模型（迁移 V12，新增 6 张表）

现状：43 张表，最新迁移 `V11__chapter_fact_layer.sql`。全部遵循 `t_` 前缀 + `user_id` 隔离 + 逻辑删。

```sql
-- 短剧项目
create table t_drama_project (
  id bigint primary key,
  user_id bigint not null,
  novel_id bigint,                    -- 可空：D-22 支持无原著
  source_chapter_from int, source_chapter_to int,
  title varchar(120),                 -- 短剧名（可与小说不同）
  form varchar(16),                   -- VERTICAL / HORIZONTAL
  episode_count int, episode_seconds int,
  adapt_level varchar(16),            -- FAITHFUL / MERGE / REWRITE
  genre varchar(32),
  character_limit int, scene_limit int,
  logline varchar(200),               -- 一句话卖点
  synopsis text,                      -- 短剧简介
  mainline_json text,                 -- 主线三段式
  status varchar(24),                 -- DRAFT/PERSONS_READY/.../READY/FAILED
  stage varchar(24), progress int,
  error_msg varchar(500),
  deleted int default 0, created_at timestamp, updated_at timestamp, version int default 0
);

-- 人物（全局字典）
create table t_drama_character (
  id bigint primary key, user_id bigint not null, project_id bigint not null,
  source_character_id bigint,         -- 映射自小说 t_character，可空（AI 新增的角色）
  name varchar(60), role_type varchar(24),   -- LEAD/VILLAIN/SUPPORT/CAMEO
  age_desc varchar(40), identity varchar(120),
  appearance varchar(500), personality varchar(500),
  motivation varchar(300), arc varchar(500),
  merge_from varchar(255),            -- 合并了哪些原著角色
  locked int default 0,
  deleted int default 0, created_at timestamp, updated_at timestamp, version int default 0
);

-- 场景（全局字典）
create table t_drama_scene (
  id bigint primary key, user_id bigint not null, project_id bigint not null,
  name varchar(80), location varchar(120),
  indoor int, time_of_day varchar(16),      -- DAY/NIGHT/DAWN/DUSK
  mood varchar(120), character_names varchar(255),
  episode_from int, episode_to int,
  locked int default 0, deleted int default 0,
  created_at timestamp, updated_at timestamp, version int default 0
);

-- 物品 / 道具
create table t_drama_prop (
  id bigint primary key, user_id bigint not null, project_id bigint not null,
  name varchar(80), first_episode int,
  function_type varchar(24),          -- PLOT / IDENTITY / CLUE
  description varchar(300), need_closeup int,
  locked int default 0, deleted int default 0,
  created_at timestamp, updated_at timestamp, version int default 0
);

-- 剧集
create table t_drama_episode (
  id bigint primary key, user_id bigint not null, project_id bigint not null,
  episode_no int not null, title varchar(120), duration_sec int,
  hook varchar(300),                  -- 前 3 秒钩子
  conflict text, twist text, cliffhanger text,
  source_chapters varchar(120),       -- 对应小说章节，如 "12-14"
  shot_count int, dialogue_words int,
  status varchar(24),                 -- PENDING/OUTLINE_OK/STORYBOARD_OK/FAILED
  locked int default 0, deleted int default 0,
  created_at timestamp, updated_at timestamp, version int default 0
);

-- 分镜（最细粒度）
create table t_drama_shot (
  id bigint primary key, user_id bigint not null, project_id bigint not null,
  episode_no int not null, scene_no int not null, shot_no int not null,
  shot_size varchar(16),              -- 远景/全景/中景/近景/特写
  camera varchar(64),                 -- 固定/推/拉/摇/跟/手持
  visual text,                        -- 画面描述
  dialogue text,                      -- 台词
  speaker varchar(60),                -- 说话人（必须能在人物表里找到）
  action text,                        -- 动作指示
  duration_sec int,
  audio_hint varchar(120),            -- 音效/BGM 提示
  remark varchar(300),                -- 实拍备注（P1 留白）
  locked int default 0, deleted int default 0,
  created_at timestamp, updated_at timestamp, version int default 0
);
```

索引：`t_drama_project(user_id, deleted)`、`t_drama_character(project_id)`、
`t_drama_episode(project_id, episode_no)`、`t_drama_shot(project_id, episode_no, scene_no, shot_no)`。

**不加 `t_drama_task`**：项目表的 `status/stage/progress` 加集表的 `status` 已经能表达进度，多一张表会出现两处状态打架。

## 七、提示词设计要点（这个功能成败在这里）

### 7.1 五阶段为什么不能合并成一次调用

一本 30 万字的小说，直接要求「输出全部短剧结构」，必然出现：人物前后重名、场景越写越多、分镜被截断、集与集之间断裂。所以要拆：

| 阶段 | 输入 | 输出 | 为什么单独 |
|---|---|---|---|
| 1 故事提炼 | 总纲 + 章节摘要（不是全文） | 卖点/简介/三段式 | 定调，后面的阶段都要参考它 |
| 2 人物 | 提炼结果 + 小说人物表 | 6~10 人 | 要做合并决策，需要全局视角 |
| 3 场景与道具 | 提炼结果 + 人物表 | 8~15 场景 + 5~10 道具 | 以人物活动范围为线索 |
| 4 分集大纲 | 提炼 + 人物 + 场景 | 每集四要素 | 一次性排完所有集，保证节奏不塌 |
| 5 分镜 | 单集大纲 + 字典表 | 该集 3~5 场 × 3~8 镜 | **逐集调用**，24 集 = 24 次 |

### 7.2 字典表必须"串"进后续每一次调用

第 5 阶段生成第 12 集分镜时，提示词里必须带上：完整人物表（只给姓名 + 身份 + 性格一句话）、完整场景表、该集大纲。**不给就得靠 AI 记忆，它会给第 8 集编个新角色。**

生成后还要做**机器校验**（D-13）：`speaker` 和 `scene_no` 是否都在字典里，不在就重试一次并附上「可用清单」。

### 7.3 输出用 JSON，但必须能容忍残缺

沿用项目已有的 `LenientJson`。分镜一集通常是 20~40 条、每条 8 个字段，一次输出 3000~5000 字，容易被截断。策略：

- 单集分镜**再按场拆**（一场一次调用），失败只重做那一场
- 解析失败时先尝试"补齐右括号"再解析，仍失败才重试
- 重试上限 2 次，仍失败标记该场为 `FAILED`，不阻塞其他集

### 7.4 复用小说已有的素材，别让 AI 重新编

小说库里已经有：`t_character`（姓名/身份/年龄/外貌/性格/动机/弧光，存在 `profile_json`）、`t_item`、`t_faction`、`t_setting_doc`（世界观/背景/核心冲突/爽点/文风）、`t_master_outline`、`t_chapter.fact_summary`。

**人物阶段应该是「映射 + 合并 + 补充」，不是「凭空生成」**：把小说人物表作为输入，让 AI 输出「保留哪些、合并哪些、删掉哪些、新增哪些」，并记录 `source_character_id` 与 `merge_from`。这样改起来可追溯，也不会把原著人设写漂。

**注意**：`fact_summary` 线上 174 章里只有 1 章有值（事实层对存量内容等于没开）。所以第 1 阶段**不能依赖事实摘要**，要退回用「章节标题 + 卷名 + 总纲 + 每章前 200 字」。等事实层回填了再优化。

### 7.5 分镜要「为拍摄而写」（二期反推的硬约束）

一期虽然是纯文字，但分镜会被二期直接送去生成视频。所以分镜提示词必须**现在就规避 AI 的死穴**，否则二期每一镜都要返工：

| 约束 | 写进提示词的原文要求 | 原因 |
|---|---|---|
| **控景别** | 正脸大段对白 ≤2 句即切走；长对白拆成「说 → 听的人反应 → 再说」 | AI 口型做不到长对白，正脸久了必露馅 |
| **单镜单动作** | 一镜只允许一个主动作（转身/抬手/走两步/低头），禁止打斗、追逐、双人肢体接触成镜 | 动作越复杂越崩，这是抽卡成本的根源 |
| **双人同框要少** | 双人同框控制在总镜数 20% 以内，冲突戏优先「单人特写交替」 | 双人同框是穿模重灾区 |
| **台词与时长匹配** | 单镜台词 ≤ 时长 × 4 字/秒，超了就拆镜 | 二期音量对不上画面，只能变速或裁切 |
| **画面可拍** | 不写心理描写，只写「看得见的东西」（表情、动作、环境、道具） | 无法生成「他心里很痛」 |

> 这五条要作为 `DRAMA_STORYBOARD` 系统提示词的固定纪律块，和小说侧的 `PromptKit.NAMING/TITLES/ANTI_MECHANICAL` 同等地位——**改分镜纪律要同步检查二期的生成成功率**。

## 八、前端入口与页面结构

新增一级菜单「短剧库」，图标建议 `Film`，路由 `/dramas`（`meta: { title: '短剧库', icon: 'Film', menu: true }`）。

```
短剧库（/dramas）
 ├─ 列表页：卡片（短剧名 / 原著名 / 集数 × 时长 / 状态 / 进度条）
 └─ 详情页（/dramas/:id）左侧导航 + 右侧内容
      ├─ 概览      卖点、简介、主线、配置回显、进度
      ├─ 人物      表格（可合并、可新增）
      ├─ 场景      表格
      ├─ 物品      表格
      ├─ 剧集      表格（钩子/冲突/反转/悬念 四列，空值标黄）
```

创建向导（`/dramas/new`）：选小说 → 选章节范围 → 填配置 → 预估「约 X 集 / Y 个镜头 / 预计消耗」→ 开始转换。

## 九、任务与成本

| 项 | 估算 |
|---|---|
| 一次完整转换的 AI 调用次数 | 约 5 + 集数（24 集 ≈ 29 次；80 集 ≈ 85 次） |
| 单次耗时 | 分镜一集 20~40 秒，整本 24 集约 15~25 分钟 |
| Token 量级 | 输入以大纲+摘要为主，整本约 60~120 万 token（取决于集数） |
| 并发 | **串行**（沿用项目对硅基流动 429 的既有教训：正文+分析并发必崩） |

**必须做的三件事**：

1. **进程内互斥**：同一项目同时只允许一个转换任务（`40090`），否则两路一起改同一张人物表。
2. **可暂停可续跑**：每集落库即算完成，重启后从未完成的集继续，不重头来。
3. **创建时给成本预估**：按集数估算调用次数与 token，让人在点「开始」前知道大概花多少。

> 参考：项目已有 `AutoWriteScheduler` 的「动态注册 + 任务表 + 进程内 running 集合」做法，短剧转换直接照这个结构做，不引入 MQ。

## 十、风险清单

| # | 风险 | 影响 | 应对 |
|---|---|---|---|
| 1 | **分镜量爆炸** | 80 集 × 4 场 × 5 镜 = 1600 镜，一次生成不可能 | 逐集逐场生成 + 懒加载 + 只生成用户要的集（「先生成前 6 集试试」） |
| 2 | **人物名漂移** | 分镜里冒出字典外的人名，整份文档不可用 | 字典串入每次调用 + `speaker` 机器校验 + 失败重试附清单 |
| 3 | **JSON 截断** | 一集分镜 3~5 千字，尾部字段丢失 | 按场拆分 + `LenientJson` + 补齐括号 + 限 2 次重试 |
| 4 | **事实层没开** | 无法用章节事实摘要做输入 | 退回「标题+卷名+总纲+章首 200 字」；先把事实层回填列为前置任务 |
| 5 | **集数配置不合理** | 30 万字配 12 集 → 每集塞 2.5 万字，必然流水账 | 创建时按字数给建议值并提示「低于建议集数会明显丢情节」 |
| 6 | **改编质量主观** | 用户觉得「不像原著」 | 提供改编力度三档；分镜整段可批注；不承诺「一次通过」 |
| 7 | **长任务中断** | 25 分钟的任务，页面关了或服务重启 | 状态落库、可续跑、已完成集不重做 |
| 8 | **导出体积** | 80 集分镜的 Word 可能 300+ 页 | 导出支持只选部分集；Word 用标题层级而非手动分页 |

## 十一、需要你定的 4 件事

| # | 问题 | 影响 |
|---|---|---|
| ① | **主打哪种形态？** 竖屏 80~100 集 × 60~90 秒，还是横屏 24 集 × 2 分钟 | 决定提示词里的节奏约束、默认集数、分集大纲的写法。两种都要也行，但模板要各写一套 |
| ② | **首版集数上限？** 建议先只支持到 24 集 | 24 集约 29 次调用、25 分钟能跑完，可验证质量；80 集是另一个量级的等待 |
| ③ | **分镜要多细？** 只到「一镜一行（景别+画面+台词+时长）」，还是要带运镜、音效、机位 | 细一分，AI 幻觉多一分，但拍摄方更需要 |
| ④ | **导出格式优先级？** Word / PDF / Excel 分镜表 / Markdown | 决定先做哪个转换器（Word 用 docx 库，CSV 最简单） |

## 十二、建议的实施顺序

1. **表 + 项目 CRUD + 创建向导**（能建出来、能看到空壳）
2. **阶段 1~3：简介 / 人物 / 场景道具**（一次调用能出结果，人工可改）
3. **阶段 4：分集大纲**（一次排完，这是最需要调提示词的一步）
4. **阶段 5：单集分镜**（先只支持「手动点第 N 集生成」，跑通再改成批量）
5. **导出 Word / CSV**
6. **一致性校验 + 锁定 + 重做**

前 4 步跑完就能拿一本真书试改编质量。**在这之前不要做前端美化**——如果第 4 步的分集大纲写出来像流水账，界面再漂亮也没用。

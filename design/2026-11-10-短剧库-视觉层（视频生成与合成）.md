## 一、两期的边界

```
一期（文字层）已完成设计
  小说 → 简介 / 人物表 / 场景表 / 道具表 / 剧集表 / 分镜表
                                                  ↓ 本文接手
二期（视觉层）
  ① 参考资产   人物视图、场景视图、道具视图      ← 定妆，锁死形象
  ② 分镜静帧   每个镜头一张首帧图                ← 定构图
  ③ 视频抽卡   每镜生成 N 个候选，择优              ← 定表演
  ④ 对白配音   每句台词一条音轨（先算时长）
  ⑤ 审片闸门   全集合规才能合成
  ⑥ 剧集合成   镜头 → 一集成片（+ 字幕 / BGM / 音效）
```

**一期不做视觉层的东西，但字段要留**（`t_drama_shot` 已有 `visual` 画面描述、`duration_sec`、`speaker`，够用，不改表）。

## 二、先回答你的问题：先配音还是先视频？

你问的这一点是整个设计的枢纽，答案不是二选一。

> **本章已被后续决策修订（2026-11-10 晚）**
> 原结论是「主链路 A（画先声后），C 只用于过场」。**现已改为以 C（原生同出）为主链路**，
> 原因是查实 Vidu Q4 的参考生视频接口接受 `sounds` 参数（最多 3 段、每段 3~12s 音频），
> 可用角色音色样本约束生成音轨——原设计不选 C 的唯一理由（音色漂移）有了工程解法。
> **以此为准**：`2026-11-10-1.4.0-短剧库需求（原生音画同出）.md`。
> 本章保留原文，作为决策过程记录；本章的 A / B 路线在新文档中降为「降级路线 / 不实现」。

### 2.1 现在市面上的三条路线（2026-11 实查）

| 路线 | 做法 | 代表能力 | 口型 | 致命短板 |
|---|---|---|---|---|
| **A 画先声后** | 图生视频出表演 → 后期贴配音 | 可灵图生视频 / Vidu 图生视频 / Runway | 靠后处理，易错位 | 时长是模型定的（5/10s），音频要迁就画面 |
| **B 声先画后** | TTS 出干声 → 音频驱动口型 | Kling Avatar V2（$0.048/s）、InfiniteTalk（$0.03/s） | **最准**，音画必然同步 | **只能口播**：单张正脸照 + 音频，动作幅度极小 |
| **C 原生同出** | 一次生成，画面和对白同时产出 | Vidu Q4 Preview（15 参考图 + 3 段参考音频，音视频联合建模）、Kling 2.6/3.0 native audio（≤10s）、Seedance 2.5（原生最长 180s） | 天然对齐 | **声音不是你写好的配音**，音色漂；改一句台词要整镜重生 |

补充数据点：Kling Lip Sync（后处理修嘴）$0.018/s，输入视频 2~10 秒、720p~1080p，人脸偏离正脸超 ~30° 会变形；网页版上限 60 秒。

### 2.2 短剧的现实决定：不能全局选一条路

短剧一集 60~90 秒，60% 以上是对话。但对话镜头的景别是混合的：

| 这一镜长什么样 | 例 | 走哪条 | 为什么 |
|---|---|---|---|
| 正脸说话，近景 / 特写 | 男女主对峙、逼问 | **B**（先 TTS 定长 → 音频驱动） | 嘴看不清就出戏，且时长必须精确到帧 |
| 说话但中景 / 侧身 / 背身 / 边走边说 | 走廊争执、车上 | **A**（图生视频 → 贴音频，**不修口型**） | 嘴看不清，硬修反而脸部崩坏 |
| 无台词 | 摔门、雨夜街、眼神反应 | **A**（纯图生视频） | 无口型需求，只铺音效/BGM |
| 旁白 / 内心独白 | 开场画外音 | **A**（画面 + 独立音轨） | 画外音无口型 |
| 关键台词、要情绪张力 | 一句定生死的狠话 | **C**（给参考音频 + 台词，一次出） | 表演和声音都到位，省一次拼接；但音色受模型影响 |

### 2.3 我的推荐：主链路 A，但「时长前置」

> ⚠️ **本节结论已作废，勿按此实施**。现行方案见 `2026-11-10-1.4.0-短剧库需求（原生音画同出）.md` §2。
> 以下文字保留，用于说明为什么最初没选 C，以及后来为什么改。

**结论：先配音，但只先算时长，不先定声音。**

具体三步：

```
1. 台词 → TTS 出干声 → 拿到精确时长 T（这是唯一硬需求）
2. 视频按 T 就近取值生成（5s / 10s），画面表演自由发挥
3. 合成时音频铺进去：
   - 非正脸镜头：到此结束，不修口型
   - 正脸特写且对不上：调一次 Lip Sync 补（新增一个 take，不覆盖原 take）
```

这样同时拿到了 A 的「表演自然」和 B 的「音画对齐」，代价是多一次 TTS 调用（几乎不要钱）。

**为什么不推荐把 C（原生同出）当主链路**：短剧人物表里每人绑定了一个固定音色，而原生同出的音色由模型决定，第 3 集和第 8 集同一角色声音会变——这是观众能立刻听出来的低级错误。C 只用在「不重要的过场台词」或「用户明确接受音色变化」时。

> **这段判断已被推翻。** 当时假设「音色完全由模型决定」，实际 Vidu Q4 支持音频参考：
> 传 3 段该角色 3~12s 的音色样本，生成音轨会向样本靠。再叠加「原生画面 + TTS 替换音轨」
> （台词相同、语速调齐，口型仍然对得上），音色漂移基本被消掉。所以 C 可以当主链路。

**首版落地建议**：~~只做 A + 可选 Lip Sync，B 与 C 留字段不做。~~ → **改为：C 为主，A 降级，B 不实现。**

## 三、参考资产库（形象定妆）

这是全链路一致性的地基。**跳过这一步，后面每一镜都在抽卡赌博。**

### 3.1 三类资产，各自要哪些视图

| 资产 | 视图 | 张数 | 用途 |
|---|---|---|---|
| **人物** | 正面半身、侧 3/4、全身、表情集（喜怒惊） | 3~5 | 视频模型的主体参考；正面那张是「主参考」，权重最高 |
| **场景** | 主视角空镜、反向机位、细节（门/窗/桌面） | 2~3 | 锁空间关系和光位 |
| **道具** | 正面、细节特写（文字/纹理） | 1~2 | 关键道具必须能认出是同一个东西 |

规范（写进提示词模板，不许模型自由发挥）：
- 尺寸：竖屏 1080×1920；横屏 1920×1080
- 人物必须**正脸或 3/4 侧**，脸部占画面 ≥25%，不能有遮挡、不能重滤镜（会抹掉身份特征）
- 同一个人物的所有视图，**服装、发型、妆容必须完全一致**（换装要单开一组资产，标 `COSTUME_B`）
- 光位写死一句话，每次生成原样复制（改光位=换人）

### 3.2 版本化：这是最容易翻车的地方

参考图改了，已经用它生成的镜头就"不是同一个人"了。所以：

- 每个资产有 `asset_version`，改图 +1
- 每个 take 记录 `input_refs_json`，内含用到的资产 id + 版本号
- 改资产 → 系统算出「有 N 个已定稿镜头引用了旧版本」→ 弹窗让用户选：
  - 只改以后（旧镜头保留，一致性自己承担）
  - 标记旧镜头为 `STALE`（待重做，进任务队列）

> 和小说侧「设定改了要重新同步」是同一个套路，`t_drama_asset` 的版本号就是 `t_setting_doc` 的 updated_at。

### 3.3 资产生成也是抽卡

一张人物正面图也要抽 2~4 次才满意。所以资产和图共用一套「候选 + 选用」结构，只是产物是静图。资产`status`：`DRAFT → APPROVED`，**只有 APPROVED 的资产才能被镜头引用**（`40096`）。

## 四、分镜静帧（首帧图）

### 4.1 为什么必须有这一步

图生视频的质量上限由首帧决定。直接把「画面描述」丢给文生视频 = 构图、景别、人物位置全靠运气，一镜一抽，24 集抽下来风格必然散。**先出静帧、审过再动**，是行业里唯一能控成本的做法。

### 4.2 静帧的输入

```
分镜行（景别 + 画面描述 + 人物 + 场景 + 道具）
  + 参考资产（人物主参考 + 场景主视角 + 道具）
  + 风格前缀（全项目统一：画风 / 色调 / 镜头语言 / 画幅）
  → 静帧候选 × N
```

风格前缀是项目级字段，**一次写死，全局注入**（`t_drama_project.style_prompt`）。这是防止「第 5 集突然变成另一种画风」的唯一手段。

### 4.3 景别对提示词的影响

| 景别 | 提示词必须带 | 参考图给谁 |
|---|---|---|
| 远景 / 全景 | 环境占 70%，人物小 | 场景为主，人物只作次要参考 |
| 中景 | 人物占 40%，环境可辨 | 人物 + 场景 |
| 近景 | 胸像，背景虚化 | 人物主参考（权重最高） |
| 特写 | 脸部/手部/道具特写 | 人物面部视图 或 道具细节图 |

## 五、视频抽卡（核心功能）

### 5.1 「抽卡」到底是什么

一镜生成 N 个候选 → 人工挑一个 → 定稿。行业里把随机性叫「抽卡」，本质是**用少量多次的生成换质量，用人工判断替代导演**。

产品化的四件事，缺一件就变成烧钱机器：

1. **候选组**：同一镜的多条 take 并列，不是覆盖式重生成（覆盖式会让你在删掉第 2 条之后才发现第 1 条更好）
2. **对比墙**：四宫格同步播放 / 逐帧步进，能对比首帧、尾帧、动作轨迹
3. **抽卡上限**：单镜默认 3 次，可调到 6；超限弹二次确认「这一镜已花 ¥X，确定再抽？」
4. **淘汰归因**：不选的理由打标签（人脸崩 / 穿模 / 动作怪 / 台词对不上 / 构图差 / 时长不对）→ 聚合统计后反向优化提示词模板

### 5.2 一镜的输入槽位（关键设计）

模型不是参考图越多越好，而是**每个槽位只放一张、职责单一**。可灵 4.0 参考生视频上限 10 图 + 7 元素；Vidu Q4 上限 15 图 + 3 音频。我们按 10 个槽位规划：

| 槽位 | 内容 | 优先级 | 说明 |
|---|---|---|---|
| S1 `start_frame` | 本镜静帧（定稿那张） | 必填 | 图生视频的首帧，权重最高 |
| S2 `prev_tail` | 上一镜定稿 take 的尾帧 | 高 | 只在 `衔接=STRICT` 时填，用于连戏 |
| S3 `character_1` | 本镜主说话人的正面视图 | 必填 | 近景/特写时权重拉满 |
| S4 `character_2` | 第二人物（双人同框才给） | 中 | **双人同框极易崩，能拆单人镜头就拆** |
| S5 `scene_main` | 场景主视角空镜 | 高 | 锁空间和光位 |
| S6 `prop_1` | 关键道具（有特写需求时） | 中 | 没有就不占槽 |
| S7 `character_1_side` | 主人物侧视图 | 低 | 侧身镜头才给 |
| S8 `character_1_full` | 主人物全身（服装/体态） | 低 | 全身/远景才给 |
| S9 `costume` | 换装态资产 | 低 | 剧情换装时替换 S3 |
| S10 空 | 保留 | — | 留给后续「动作参考视频」 |

**裁剪规则**（写进代码，不让用户配）：按上表优先级从高到低填，超上限就砍尾部的。同一主体**不许**占两个槽以上（除 S7/S8 的特例）。

### 5.3 提示词结构：锁 + 动作 + 运镜 + 声音

参考图锁形象，提示词只写「要发生什么」。三段式（借鉴 Vidu 的 lock–action–camera–sound）：

```
[锁] 保持参考图中同一人物：<外貌一句>；同一场景：<光位一句>。
     （不许重写外形——重写就是让模型重新发明这个人）
[动作] 0-2s ____；2-4s ____；4-5s ____。    ← 秒级切分，动作必须简单
[运镜] 中景，缓慢推近，浅景深。单一运镜，不切镜。   ← 一镜只有一个运镜
[声音] 环境音：____；台词：____（或留空，音频后期贴）
[禁止] 不变形、不换脸、不穿模、无字幕水印、无多手多指
```

**动作复杂度是崩坏的头号原因**：单镜只允许「一个主动作」（转身 / 抬手 / 走两步 / 低头）。打斗、追逐、双人肢体接触必须拆镜。

### 5.4 生成必须异步任务化（技术硬要求）

视频接口全是异步：提交拿 `task_id` → 轮询 → 出文件。单次 30 秒~5 分钟，比图片的 10~60 秒长一个量级。

**禁止**把轮询塞进 HTTP 请求线程（现有 `ImageGenClient` 阻塞轮询 240 秒的做法，视频不能照抄）：
- Tomcat 线程会被占死，2 核机器撑不住几个并发
- 前端 axios 默认 30 秒超时（项目已有教训）
- 关页面就断

正确做法：

```
POST /shots/{id}/takes  →  落库 take(status=QUEUED) → 立即返回 takeId（202）
        ↓  后台 @Scheduled 每 10s 扫 QUEUED/RUNNING
   提交远端 → 存 remote_task_id(status=RUNNING) → 轮询
        ↓  成功：下载 mp4 到本地 → 抽首帧/尾帧 → 生成缩略图 → status=SUCCEEDED
        ↓  失败：记 error_msg，退避重试 2 次
前端 SSE 订阅进度（沿用 ContentStreamService 的 meta→delta→done 模式）
```

并发上限：**全局 2 路**（不是每用户 2 路）。理由和硅基流动 429 的教训一样——1G 内存 + 2 核，同时 4 个下载 + FFmpeg 抽帧就会 OOM。

### 5.5 尾帧衔接（连戏）

用户明确要求了「前一分镜最后画面」作输入。落地要点：

- 每个 `SUCCEEDED` 的 take 落库时，用 FFmpeg 自动抽**尾帧**存图（`-sseof -0.1 -frames:v 1`，不吃内存）
- 下一镜可选三种衔接模式：
  - `STRICT` 严格：上镜尾帧作为本镜首帧（**本镜静帧作废**）——适合连续动作，但会牺牲构图
  - `LOOSE` 宽松：尾帧只作参考图放 S2 槽，本镜静帧仍是首帧 —— 默认
  - `OFF` 关闭：场景切换、跳切、时间跳跃时用
- **顺序约束**：只有上一镜**定稿**后才允许 STRICT。所以生成顺序必须是线性推进（第 3 镜没用 STRICT 需求时可以和第 2 镜并行）

## 六、配音与口型

### 6.1 音色要先绑定，不要每句现选

人物表里每人绑一个音色（`t_drama_voice`）：`character_id → voice_id + 语速 + 情绪基线`。**音色是一次性决策，全局复用**，否则同一角色跨集会变声。

音色来源：供应商内置音色库（可灵 46 个内置音色 / 各家 TTS）+ 可选的声音克隆（需授权，**首版不做**）。

### 6.2 台词拆句规则

分镜的 `dialogue` 字段可能是「你终于来了。我等了你三年。」——一条音轨读下来节奏会平。所以：

- 按说话人 + 句号/问号/叹号切分成 `t_drama_line`，一句一条音轨
- 每条带 `emotion`（平静/愤怒/哽咽/嘲讽）和 `speed`，这两个参数直接影响时长
- **同一镜多条台词**：分别生成，按 shot 内顺序排时间轴；重叠的话（抢话）允许 `start_offset_ms`

### 6.3 口型：默认不修，有需要才修

| 情形 | 处理 | 成本 |
|---|---|---|
| 中景以上 / 侧身 / 背身 / 走动说话 | **不修**。景别天然掩盖 | 0 |
| 正脸近景 / 特写且时长 ≤10s | 调 Lip Sync 修一次（可灵 $0.018/s） | ¥0.9/5s |
| 正脸特写且 >10s | 拆成两个镜头再修，或改用 Avatar 重建该镜头 | 中 |
| 修复后仍崩 | 放弃口型，改景别（切背影/反应镜头/加旁白） | 0 |

**产品上必须给的兜底**：`POST /takes/{id}/lip-sync` 生成的是一条**新 take**（`route=LIP_SYNC`，`parent_take_id` 指向原 take），原 take 保留。修坏了能退回去。

> 一句实话要写进 UI 提示：**AI 口型做不到真人级别，长对话必然露馅**。所以分镜阶段就应该「多用中景、少给大段正脸对白」——这条要写进一期 `DRAMA_STORYBOARD` 的提示词约束里（一期文档需补一条）。

## 七、审片闸门（你说的「审核所有分镜都满意」）

这是从「生成」跳到「合成」的唯一通道，必须是硬闸门，不能靠自觉。

### 7.1 一集的镜头状态机

```
PENDING          未生成
FRAMED           静帧已定稿
TAKED            有可用 take（已选用 1 条）
APPROVED         人工点了「过」        ← 闸门看这个
NEED_FIX         人工点了「不行」（带原因）
```

`t_drama_episode.render_status`：`NOT_READY → READY → BUILDING → RENDERED → FAILED`

**合成前置条件**：该集全部非空镜头都是 `APPROVED`，且集内无 `NEED_FIX`。否则返回 `40097` 并列出「还有 N 镜没过」。

### 7.2 审片的两个视角（都要有）

1. **单镜检查**：这一镜的候选墙 → 挑一个 → 过 / 重抽
2. **整集连看**：把所有 APPROVED 的 take 按序拼一个**低码率预览片**（480p，`-c copy` 到低码率不现实，所以用 480p 重编码，但 480p 重编码内存只要 ~80MB，1G 机器可以接受）→ 连着看节奏对不对

**整集连看是必须的**：单镜都好看，连起来可能节奏塌、人物位置跳、光线接不上。这是审片的真正价值。

## 八、剧集合成

### 8.1 合成清单（一次合成 = 输入确定的产物）

```
镜头序列：[(shot_id, take_id, 入场方式, 转场), ...]
音轨：对白 line[] + 旁白 + BGM（音量 0.2~0.25）+ 音效
字幕：由 line[] 自动生成 srt，样式统一
片头/片尾：可选
规格：1080×1920 / 30fps / H.264 / yuv420p / AAC 48k
```

### 8.2 技术路线：`-c copy` 拼接，禁止全局重编码

**这是 1G 内存机器上唯一可行的方案。**

```bash
# 1) 拼接：视频流不重编码，秒级完成，内存 ~30MB
ffmpeg -f concat -safe 0 -i list.txt -c copy -y video.mp4

# 2) 混音：只有音频流重编码，内存 ~50MB
ffmpeg -i video.mp4 -i bgm.m4a -filter_complex \
  "[1:a]volume=0.22[b];[0:a][b]amix=inputs=2:duration=first:dropout_transition=0" \
  -c:v copy -c:a aac -b:a 128k -y mixed.mp4

# 3) 软字幕：不烧录，播放器可关
ffmpeg -i mixed.mp4 -i sub.srt -c copy -c:s mov_text -y final.mp4
```

代价与红线：

| 限制 | 原因 | 应对 |
|---|---|---|
| 所有镜头必须**同分辨率/帧率/像素格式/音频参数** | `-c copy` 只拼流，参数不一致会花屏 | 抽卡时就统一规格；不合规的 take 落库时用 FFmpeg 转一次（单条 5 秒转码内存 ~300MB，可接受） |
| **不能加转场**（叠化/擦除） | 转场必须重编码相邻两镜 | 首版只做硬切 + 首尾黑场；转场留给用户本地剪 |
| 字幕是软字幕 | 烧录要重编码整集 | 需要硬字幕时提供「本地包」让用户自己烧 |
| 音量归一化跨镜头 | 不同 model 出的音轨响度不一 | 混音时对每条 line 先 `loudnorm`（单条处理，内存低） |

### 8.3 可重入

改了第 3 镜 → 重新合成 → **不重新生成任何镜头**。`t_drama_render` 每次合成新建一条记录（保留历史），带 `shot_list_json` + `ffmpeg_cmd`，可复现、可对比。

### 8.4 导出包（给要精修的用户）

一键打包 zip：所有 APPROVED 的 take 原片（按 `E01_S01_C01.mp4` 命名）+ 分轨音频（对白/旁白/BGM/音效分目录）+ `字幕.srt` + `剪辑清单.csv` + 可选 `剪映草稿`（P2）。

> 这个功能成本极低（只是打包），但价值很高：AI 合成做不到人剪的节奏，很多用户最终还是要进剪映。

### 10.1 新增接口类型（`AiConfigKind`）

现有只有 `TEXT` 和 `IMAGE`。要加两个：

```java
TEXT("文本接口"), IMAGE("图像接口"), VIDEO("视频接口"), TTS("语音接口");
```

## 十一、架构与硬约束（这一节决定方案能不能落地）

### 11.1 实测的服务器现状（2026-11-10 查）

| 项 | 实测 | 影响 |
|---|---|---|
| CPU | **2 核** | FFmpeg 重编码 1080p 会跑满两核，应用卡死 |
| 内存 | **1 GB**（可用几乎为 0） | 1080p 重编码峰值 800MB~1.5GB → **必 OOM** |
| 磁盘 | 40GB，已用 8.2G，**剩 32G** | 见下方容量测算 |
| Docker 镜像 | 3.87GB（可回收 1.79GB） | 可先回收腾 1.8G |

### 11.2 容量测算（这是最硬的约束）

竖屏 1080×1920 / H.264 / 4Mbps ≈ 0.5MB/s：

| 项 | 24 集 | 80 集 |
|---|---|---|
| 成片（90s/集） | 1.1 GB | 3.6 GB |
| 抽卡素材（每镜 3 抽，废片全留） | 6.5~11 GB | 22~36 GB |
| 静帧 + 参考图 | 0.8 GB | 2.7 GB |
| 台词音频 | 0.1 GB | 0.3 GB |
| **合计** | **8.5~13 GB** | **29~43 GB** |

**结论：剩余 32G 装不下一个 80 集项目的全流程素材。** 必须三选一（建议 1+3 组合）：

1. **素材走对象存储**（腾讯云 COS，同区域走内网，下行免费）。本地只存 `cover_url` 缩略图和 DB 记录。这是正解。
2. **自动清理**：废片（`judge=REJECTED`）保留 7 天自动删；成片导出后本地只留最近 3 集。
3. **升配磁盘**到 100G（成本低，一次性）——但内存 1G 的问题升盘解决不了。

### 11.3 合成放在哪跑

| 方案 | 可行性 | 评价 |
|---|---|---|
| **云端 `-c copy` 拼接** | ✅ 可行 | 30MB 内存、秒级。**首版选这个** |
| 云端重编码（加转场/烧字幕） | ❌ 1G 内存不行 | 需要 8G 内存；要么升配，要么不做 |
| 桌面版本地合成 | ✅ 可行 | 用户自己的 CPU；但要装 FFmpeg，且桌面版是 sqlite 模式，素材在本地反而方便 |
| 云端只出素材包，用户在剪映合成 | ✅ 最省事 | 成本 0，但用户要多一步 |

**落地顺序建议**：先做「素材包导出」（一天的事，立刻能用），再做「云端 copy 拼接」，重编码类功能（转场/烧字幕）放到桌面版或远期。

### 11.4 必须引入 FFmpeg

项目目前**没有 FFmpeg 依赖**。需要的动作：

- Docker 镜像里 `apt install ffmpeg`（约 +80MB 镜像）
- 抽尾帧、抽首帧、生成 480p 预览、拼接、混音、软字幕 —— 全部靠它
- 统一封装成 `FfmpegService`，**所有命令带超时和输出截断**（防止卡死占线程）

### 11.5 并发与排队

- 视频生成并发：**全局 2**、每用户 1
- FFmpeg 并发：**全局 1**（2 核不能并行编码）
- 排队策略：**同一集内严格按镜号顺序**（因为尾帧衔接），跨集可并行但受全局并发限制
- 失败重试：视频任务退避 2 次（30s / 120s），仍失败标 `FAILED` 不阻塞其他镜

## 十二、成本测算（竖屏 24 集 × 90 秒）

假设：2160 秒成片、平均 5 秒/镜 ≈ 432 镜、每镜平均生成 3 次（1 次选中 + 2 次废）。

| 项 | 量 | 单价 | 小计 |
|---|---|---|---|
| 视频生成（Vidu Q3 档，$0.042/s ≈ ¥0.30） | 432×3×5s = 6480 秒 | ¥0.30/s | **¥1,944** |
| 视频生成（可灵 4.0 参考生视频档，$0.157/s ≈ ¥1.13） | 6480 秒 | ¥1.13/s | **¥7,322** |
| 静帧（432 镜 + 50 张资产，抽 2 次） | ~960 张 | ¥0.10/张 | ¥96 |
| 配音 TTS | 约 7 万字 | ¥0.1/千字 | ¥7 |
| 口型修复（40% 镜头，5s/次） | 864 秒 | ¥0.13/s | ¥112 |
| 合成算力 | 本地 | — | ¥0 |

**单集成本：¥80~150（便宜档）到 ¥300~400（可灵 4.0 档）**
**24 集总成本：¥2,200~3,800 或 ¥7,500~9,000**
**80 集竖屏：约为 24 集的 3.3 倍（集数比）**

这三行数字必须在**点「开始抽卡」之前**显示给用户，并且：
- 创建项目时就给「预计总成本」
- 每个镜头抽卡时显示「本镜已花 ¥X」
- **必须有「先试拍 1 集」**的功能，不要一上来就整本

> 便宜档还是贵档的选择，本质是「一致性 vs 画质」。建议：**资产定妆用贵档，批量抽卡用便宜档**——定妆只生成 50 张，不差钱；抽卡 1300 次，差 5 倍。

## 十三、风险清单

| # | 风险 | 影响 | 应对 |
|---|---|---|---|
| 1 | **磁盘爆满** | 服务整体不可用（PG 写不进去） | COS + 废片 7 天清理 + 配额告警；合成本地优先 |
| 2 | **1G 内存 OOM** | 进程被杀，长任务全丢 | 禁重编码、FFmpeg 串行、`-threads 1` 限核、JVM 堆调小 |
| 3 | **人物跨镜变脸** | 成片不可用，等于白烧钱 | 参考资产版本化 + 每镜必带主参考 + 逐镜人脸校验（可选开源 face-embedding 比对） |
| 4 | **抽卡成本失控** | 单集烧掉几百块 | 单镜上限 3、超限二次确认、实时成本看板、先试拍一集 |
| 5 | **口型对不上** | 观众出戏 | 默认不修，靠景别规避；修也只修正脸近景；修不好换景别 |
| 6 | **双人同框崩坏** | 大量返工 | 提示词层面禁止双人复杂互动；能拆单人镜头就拆 |
| 7 | **长任务中断** | 3 分钟一镜的任务，页面关了/服务重启 | 任务落库 + 轮询器接管 + `remote_task_id` 可续查（远端通常保留 24h） |
| 8 | **供应商涨价/下架** | 已生成内容无法重做 | `params_json` 存全量请求快照；`VIDEO` 端点可切换供应商；不锁死单一厂商 |
| 9 | **合规** | 平台限流/下架 | AI 生成标识（片尾+元数据）、肖像权提示、禁止真人换脸 |
| 10 | **一致性校验只看图不看动** | 静态一致了，动起来还是崩 | 审片必须「整集连看」，不能只过单镜 |

---

## 十四、分期实施

### 阶段 1｜能出图、能抽卡、能看（最小可验证闭环）

1. V13 迁移 + `AiConfigKind.VIDEO/IMAGE` + `VideoGenClient`（异步任务 + 调度器）
2. 参考资产：生成 → 抽卡 → 定稿（人物三视图跑通）
3. 静帧：生成 → 选定
4. 单镜抽卡：一镜 2~3 take，四宫格对比，选用/淘汰
5. **先只做 1 集 1 场 3 镜**，跑通端到端
6. 成本看板 + 抽卡上限

> 这一步做完就能判断「这个模型能不能用在我们的分镜上」。**在这之前不要做合成**。

### 阶段 2｜能配音、能连看、能合成

7. 音色绑定 + TTS 台词
8. 尾帧抽取 + 衔接模式
9. 480p 整集预览（连看审片）
10. 审片闸门（`APPROVED` 才能合成）
11. `-c copy` 拼接 + 混音 + 软字幕 → 一集成片
12. 素材包导出（zip）

### 阶段 3｜规模化与质量

13. 批量抽卡（按集排队，全局 2 并发）
14. Lip Sync 后处理
15. 资产版本变更 → 标记 STALE → 批量重做
16. 人脸一致性自动校验（跨镜 embedding 比对，低于阈值标黄）
17. 软字幕烧录 / 转场（需升配或桌面版）

**明确不做（首版）**：声音克隆、数字人直播、真人换脸、多语种配音、自动配乐生成、4K。

## 十六、一句话总结

**文字层是「写好」，视觉层是「拍出来」。**
视觉层的本质不是「调模型」，是**管住三件事**：形象不漂（参考资产版本化）、钱不失控（抽卡上限 + 先试拍）、盘不爆（COS + 废片清理）。
这三件事管的住，模型换哪家都能用；管不住，模型再强也出不了片。

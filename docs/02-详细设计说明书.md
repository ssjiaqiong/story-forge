## 1. 文档说明

### 1.1 目的

说明 StoryForge 的总体架构、后端与前端设计、关键流程、数据模型与部署形态，作为开发维护与问题排查的索引。

### 1.2 设计范围

账号与权限、设置中心（AI 接口 / 场景绑定 / 联网搜索 / 提示词模板）、书架与 AI 开书、小说工作台（设定 / 总纲 / 章节 / 人物 / 属性背包 / 势力 / 物品 / 事件 / 分析 / 按分析修改 / 智能助手 / 封面）、导入导出、灵感模式、拆书改编、仪表盘、超管平台、多数据库、容器与桌面部署。

### 1.3 设计原则

1. **单实例、少中间件**：只依赖数据库与本地文件系统；限流、黑名单、任务状态都在进程内或库内。
2. **数据隔离下沉**：隔离由 MyBatis-Plus 数据权限插件统一追加，业务 SQL 不写 `user_id` 条件。
3. **方言收敛**：业务代码不写数据库专有语法；确需分支时走 `_databaseId`。
4. **AI 统一入口**：所有模型调用经 `AiUsageService`，保证计费、日志、重试一致。
5. **提示词分层**：用户只改指令段，输出格式契约由系统锁定，保证解析稳定。
6. **可搬运**：小说全量数据可序列化为版本化 JSON，导入时整体重建并重映射 ID。

### 1.4 术语与约定

- `user_id` 为隔离字段；雪花 ID 在接口层一律以**字符串**下发（避免 JS 精度丢失）。
- 时间统一由应用侧写入，不依赖数据库时钟（SQLite `CURRENT_TIMESTAMP` 为 UTC）。
- 逻辑删除统一用 `deleted`（0/1），唯一索引包含 `deleted` 条件。

## 2. 系统架构

### 2.1 总体架构

```text
浏览器 (Vue3 SPA)
   │  HTTPS
   ▼
Nginx（443 终止 TLS，反代 127.0.0.1:8080，关闭响应缓冲）
   │
   ▼
Spring Boot 单进程（端口 8080）
   ├─ SecurityFilterChain：JwtAuthenticationFilter（解析令牌 → 黑名单 → 账号状态 → 强制改密）
   ├─ Controller (REST) → Service → Mapper (MyBatis-Plus)
   ├─ 基础设施：AI 客户端 / 图像客户端 / 搜索客户端 / 本地文件存储 / 限流 / 审计
   └─ 静态资源：classpath:/static（前端构建产物，SPA 回退 index.html）
   │
   ├── PostgreSQL / MySQL / SQLite（业务数据）
   └── data/ 目录（封面、业务文件、日志、桌面版数据库）
```

### 3.2 通用能力

| 能力 | 实现要点 |
|---|---|
| 统一响应 | `R<T>{code,message,data,traceId}`；分页 `PageResult<T>{records,total,page,size}` |
| 错误码 | `ErrorCode` 枚举（code + message + httpStatus），全局异常处理器输出 `code`；业务异常 `BizException` |
| 参数校验 | Bean Validation；`HttpMessageNotReadableException` 转为 `10001` 并回显可选枚举值 |
| 用户上下文 | `UserContextHolder`（ThreadLocal，`set/clear`）；异步线程必须自行 set/clear |
| traceId | `TraceIdFilter` 生成并写入 MDC，响应体与日志同时带出 |
| 限流 | `@RateLimit(dimension=IP/USER, limit, windowSeconds)`，AOP 取令牌，超限 `429 / 90002` |
| 审计 | `@Audit(action, targetType, targetIdIndex)`，AOP 记录用户、IP、结果、错误摘要到 `t_audit_log` |
| ID 序列化 | `JacksonConfig` 把 Long 序列化为 String，前端 ID 一律 string |
| 自动填充 | `AuditMetaObjectHandler` 填 `created_at/created_by/updated_at/updated_by/user_id` |

### 3.3 数据隔离（核心）

1. **登记**：`application.yml` 的 `storyforge.data-permission.managed-tables` 列出所有业务表（当前 30 张）。
2. **改写**：`UserDataPermissionHandler implements MultiDataPermissionHandler`，在 SQL 解析阶段对登记表追加 `user_id = <当前登录用户>`；`UserContextHolder` 为空（登录前）不追加。
3. **二次校验**：Service 按 ID 读取时校验归属，越权统一按「资源不存在」返回。
4. **跨用户读**：超管查询通过 `DataPermissionContext.withoutIsolation(Supplier)` 在单次调用内放行，用完即恢复。
5. **公共表不登记**：`t_user`、`t_audit_log`、`t_token_blacklist` 属于平台表，不做自动隔离。

### 3.4 认证与令牌

```text
POST /api/auth/login
  → 查用户（含已删除判断）→ 状态校验 → BCrypt 校验 → 签发 access(30m)/refresh(7d)
  → 更新 last_login_*（旧的转存 prev_login_*）→ 返回 R{accessToken, refreshToken, user}

每次请求 JwtAuthenticationFilter：
  解析 Bearer → 验签 → 查黑名单(jti) → 查用户状态 → must_change_password 拦截（仅放行 me/password/logout）
  → 写 SecurityContext + UserContextHolder → finally 清理
```

- `SecurityConfig` 放行：`/api/auth/login|refresh|register`、`/actuator/health/**`、`/v3/api-docs/**`、`/swagger-ui/**`、`OPTIONS`；`/api/admin/**` 需 `SUPER_ADMIN`；其余 `/api/**` 需登录。
- 刷新令牌一次性轮换：旧 `jti` 入 `t_token_blacklist`，按 `expires_at` 定期清理。
- 密码策略与初始改密：`must_change_password` 字段；超管重置口令后置 1。
- 注册关闭：`POST /api/auth/register` 直接返回 `30030`。

### 3.6 AI 客户端

**文本**：`infra/ai/OpenAiClient`

- 请求体最小化：不带 `max_tokens`/`temperature` 默认值，避免推理模型 4xx。
- 若因采样参数被拒，自动去掉参数重试一次。
- `AiUsageService` 外层对网络错误与 5xx 重试（最多 2 次），最终失败写 `t_ai_usage(success=0)`。
- 默认 `stream=false`；**正文场景额外支持流式**：`chatStream(...)` 请求体带 `stream:true` 与
  `stream_options.include_usage`，用 `BodyHandlers.ofLines()` 逐行读 SSE。
  默认同步版本的行为完全不变。

**图像**：`infra/ai/ImageGenClient`

| `ImageProvider` | 协议要点 |
|---|---|
| `OPENAI` | `/images/generations`，同步返回 b64 或 url |
| `SILICONFLOW` | OpenAI 兼容，字段略有差异 |
| `VOLCENGINE` | 火山方舟 Seedream，`/images/generations` |
| `ZHIPU` | CogView，同步返回 url |
| `DASHSCOPE` | 百炼通义万相，**异步任务**：提交拿 `task_id` → 轮询 `/tasks/{id}` |
| `MODELSCOPE` | 魔搭，异步任务提交 + 轮询 |

**解析**：`LenientJson` 容忍模型在 JSON 字符串里输出真实换行、末尾逗号、代码块围栏等常见瑕疵。

### 3.7 提示词体系（三段式）

```text
最终 system 提示词 =
  ① 场景默认/用户覆盖的「指令段」（可编辑，入库 t_prompt_template）
  ② 上下文区块（调用方按场景注入，如人物档案、事件池、前文结尾）
  ③ 输出格式契约（PromptSceneRegistry 提供，只读，永远不入库）
```

- `PromptSceneRegistry`：登记 17 个场景的默认指令段、可用变量、输出契约。未登记的场景（`FACTION_BUILD`、`COVER_TITLE`、`INSPIRATION_CHAT`、`NOVEL_AGENT`、`DECONSTRUCT`）不开放模板编辑。
- `PromptTemplateRenderer`：替换 `{{变量}}` → 追加契约；未识别的变量由保存时校验拦截（`40005`）。
- 渲染失败（缺变量、模板损坏）回退内置默认并记 warning，生成不中断。
- `PromptKit`：公共提示词片段（反 AI 味、字数要求、世界观/文风注入等），供各 Service 复用。

#### 3.7.1 变量分层与按需裁剪

变量分两层，避免「模板里想引用设定却引用不到」：

| 层 | 例子 | 来源 |
|---|---|---|
| 表单变量 | `novelTitle`、`genre`、`idea`、`targetLength` | 建书表单 / 生成弹窗传入 |
| 上下文变量 | `worldview`、`background`、`coreConflict`、`highlights`、`style`、`constraints`、`characters`、`items`、`events`、`previousSummary`、`authorRequirement`、`searchResults` | 服务端从库中拼装 |

上下文变量本来由代码拼在 user 消息里。为避免同一份设定发两遍：

1. 各 Service 先拼好 vars、交给 `PromptTemplateService.system(scene, vars)` 渲染指令段；
2. 再取 `PromptTemplateService.usedVariables(scene)`——当前生效模板里实际引用了哪些变量；
3. user 消息的每个区块用 `PromptVars.emit(used, "worldview")` 守门：模板已引用就不再输出。

默认模板只引用表单变量，`used` 为空集合，`emit` 恒为 true，因此默认行为与裁剪机制引入前完全一致；只有用户主动引用才触发裁剪。变量值与 user 段被裁掉的那一块同源、同截断长度（集中在 `PromptVars`），否则「模板引用了变量」反而拿到更少信息。

#### 3.7.2 创作约束（建书前追问）

作者在建书表单里只填了创意、题材、风格这类粗粒度字段时，AI 需要靠猜来设计世界观与人物。因此建书前增加一步追问：

1. `POST /api/bookshelf/blueprint/questions`：AI 判断「要写好这个故事还缺什么」，最多 4 个问题；
2. 问题字段受 `NovelConstraintField` 白名单约束（`protagonist`/`goal`/`antagonist`/`power`/`world`/`opening`/`ending`/`tone`/`taboo`），模型自创的 key 一律丢弃，落库结构不会被换说法写乱；
3. `POST /api/bookshelf/blueprint/constraints`：把作答拼成「中文名：答案」逐行文本（空答案丢弃、换行抹平、总长 2000 字上限）；
4. 约束随 `BlueprintRequest.constraintText` 进入蓝图四段，建书时落库到 `t_novel.constraint_text`；
5. 此后所有创作场景（蓝图四段、总纲、大纲、正文、角色、物品、事件）把 `constraint_text` 作为模板变量 `constraints` 注入，user 段里以`【创作约束（作者已确认，必须遵守）】`呈现，作者在工作台「设定」里改一次即可影响后续全部生成。

追问是锦上添花：接口失败或返回空列表时前端直接进入生成，绝不阻塞建书。

### 3.10 关键流程

#### 3.10.1 生成一章正文

```text
POST /chapters/{id}/generate
  1. 校验章节归属与状态（DONE 拒绝）
  2. 组装上下文：本章大纲与关联事件 → 参与人物（档案 + 属性/背包 + 势力职位）
     → 相关物品 → 相关势力 → 上一章结尾 500 字 → 前 10 章大纲 → 前 50 章概括
     → 世界观/文风设定 → 联网资料（可选）
  3. PromptTemplateService.system(BODY_GEN, vars) 生成 system（指令段 + 契约）
  4. AiUsageService.chat(BODY_GEN, endpoint, messages)（重试、用量落库）
  5. 解析正文 → 覆盖或追加 → updateChapter 重算汉字数与小说字数
  6. 返回正文与引用来源
```

#### 3.10.2 章节分析

```text
POST /chapters/{id}/analysis
  1. 顺序校验：前面章节必须都有分析记录（否则 40040）；正文为空 40041
  2. 本地统计 AI 味信号（套话密度、重复句首、段落离散度、均句长、对话占比）
  3. 两次模型调用：
     a. ANALYSIS_GEN：字数核对 + 大纲贴合 + AI 率（本地信号作为硬证据，评分设上限）
     b. SYNC_EXTRACT：结构化抽取人物/物品/势力/属性/背包变化 + 事件状态
  4. 事务内落库：补新人物 → 写 change_history（原状态取分析前库内值）
     → 更新属性/背包当前值 → 本章关联事件改状态 → 保存报告 result_json
  5. 返回报告
```

#### 3.10.3 导入重映射

```text
POST /api/bookshelf/novels/import
  1. 校验 format/formatVersion；标题去重加序号
  2. 事务开始
  3. 新建小说 → 设定 → 总纲（记录 oldId→newId）
     → 势力 → 成员（映射 characterId）→ 人物 → 关系（重排 from<to，去重）
     → 属性 → 物品 → 背包（映射 itemId）→ 事件 → 参与者
     → 章节（映射 masterOutlineId）→ 章节人物/事件
     → 分析（映射 chapterId）→ 履历（映射多态 entityId）→ 助手会话与消息
  4. 封面：解码 Base64 → 写新目录 → 插入记录（超过 5 张丢弃）
  5. 任一步失败：回滚事务 + 删除已写封面文件
```

#### 3.10.4 智能助手一轮执行

```text
POST /api/novels/{novelId}/agent/messages
  1. 载入会话消息（条数/字符预算）
  2. buildSnapshot：小说元信息、设定摘要、人物、物品、势力、事件、章节（各有上限）
  3. systemPrompt：可用操作清单（CREATE/UPDATE/DELETE + 各类实体）+ 输出 JSON 约束
  4. 模型返回 {done, reply, operations[]}
  5. executeOperations：逐条执行，按类型分发；关系/成员允许用名称引用同批新建对象
  6. 未完成且未超 6 轮 → 带执行结果继续下一轮
  7. 落库助手消息 → 返回 reply + 操作清单
```

#### 3.10.4.1 智能助手分步任务（`/plans`）

单轮 + 6 轮上限只能覆盖「一次说清的小改」。复杂指令（「重建全部总纲 + 补齐章节大纲」）
会被模型挤进一轮，实测出现过**输出被截断、只建到第 5 条就停、要作者说「继续」才往下走**。
`/plans` 把这类指令变成**有状态的任务**：先规划、再连续跑、进度可查、可暂停可续。

```text
POST   /api/novels/{novelId}/agent/plans               {content}  → 建计划，立即返回 PLANNING
GET    /api/novels/{novelId}/agent/plans/{planId}                 → 计划 + 全部步骤（前端 1.5s 轮询）
GET    /api/novels/{novelId}/agent/plans/latest                   → 刷新页面后恢复任务卡
POST   .../plans/{planId}/pause | /resume
DELETE .../plans/{planId}                                         → 取消
```

**三段式流水线**（`NovelAgentPlanService`，独立线程池 `agent-plan-N`）：

| 阶段 | 做什么 | 关键约束 |
|---|---|---|
| 规划 | 用 `PLANNER_INSTRUCTION` 让模型只输出 `{"steps":[{"title","detail"}]}`，**不执行 operations** | 2~8 步（`MAX_STEPS=8`），超出截断；解析失败 → `40081` 并把计划置 FAILED |
| 落库 | 写 `t_novel_agent_plan` + 逐条 `t_novel_agent_plan_step`（PENDING） | `uk_novel_agent_plan_step(plan_id, step_no)` 防重 |
| 执行 | 逐步 `runStep`：每步最多 3 轮（`MAX_TURNS_PER_STEP`），把本步已做的操作摘要喂回去 | 只带「【当前步骤】」上下文，不看后面步骤 |

**连续执行**：跑完一步立刻推进下一步，中间不需要作者介入；每步结束写一条助手消息
（「第 N 步「xxx」已完成：…」），会话记录与任务进度对称。

**进度**：`percent = min(99, 5 + done*95/total)`，完成时由状态置 100。要留 1% 表示「还在跑」，
否则前端进度条卡在 99% 与 100% 之间看不出差别。

**暂停 / 继续 / 取消**

- `pause` 只置标记（`PAUSED` + `pausedReason`），**当前这一步做完才停**，不会把半步操作丢掉。
- `resume` 把 PENDING 的步骤接着跑完；已 DONE 的不重做。
- `cancel` 置 `CANCELLED`，未开始的步骤保持 PENDING（不改成 SKIPPED，保留原样更利于复盘）。
- 连续 `PAUSE_AFTER_FAILED_STEPS=2` 步失败自动暂停，`pausedReason` 写明原因，避免一路空跑到尾。

**重启恢复**：`ApplicationReadyEvent` 里把残留的 `PLANNING/RUNNING` 计划置 `PAUSED`
（原因「服务重启，任务已暂停，可点继续」），并把 RUNNING 的步骤回退 PENDING。
不这么做的话，重启后前端看到 RUNNING 会一直轮询一个永远不动的任务。

**前端呈现（AgentPanel）**

- 任务卡渲染在对话列表**末尾**（`.agent-list` 内），跟消息一起滚动。挂在列表外会一直浮在
  顶部把对话挤掉，看起来像「悬浮的弹窗」而不是对话的一部分。
- 整卡可折叠：进行中默认展开（要看得见每一步在做什么），进入 DONE/FAILED/CANCELLED 自动
  收成一行（`任务计划 · 已完成 · 3/3 步 · 100%` + 细进度条）；用户手动点过后不再自动开合。
- 单步回复默认只留**一行**预览，点步骤行展开全文（`.aplan-step.is-open` 取消行数限制并
  自行滚动），否则几条长回复就能把卡片撑满一屏。
- 暂停/继续/取消在卡片头右侧，`@click.stop` 避免误触折叠。

**写库注意**：状态/进度一律走 `lambdaUpdate().set(...)`，且**同一列只能 set 一次**——
PG 遇到 `SET percent = ?, percent = ?` 直接报「对同一列 percent 进行了多次分配」，
把「完成」写成了「失败」（自测时踩到过）。`updateById` 另外还会跳过 null，
清 `paused_reason` 只能靠显式 `set(...)`。

#### 3.10.5 TXT 导出

```text
GET /api/bookshelf/novels/{id}/export/txt?scope=all|volume|range&volumeNo=&from=&to=
  1. 校验范围参数（按卷缺 volumeNo、区间缺参或 from>to → 10001）
  2. 取小说（数据隔离，查不到 404）与全部章节，按 sort_no、id 升序
  3. 过滤：范围内 → 正文为空且 !includeEmpty 时跳过
  4. 按卷分组拼块：
       卷名块   volume_title 非空原样，否则「第 N 卷」
       章节块   「第 N 章 {title}」；title 已以「第 N 章/回/节」开头则原样
                title 为空则只写「第 N 章」；正文 normalize（统一换行、去首尾空行）
     块之间固定一个空行（String.join），不产生连续空行
  5. 末尾统计行：全书用 t_novel.word_count，按卷/区间用导出章节字数累加
  6. bom=true 时在开头拼 \uFEFF，Controller 按 UTF-8 转字节；
     Content-Disposition 双写 ASCII 名与 filename*=UTF-8''{书名}.txt
```

不做模板化，格式写死在服务里：不同平台的差异只有编码与章节标题，这两项已由参数覆盖；
段首缩进按「不加」处理，因为各平台偏好不同，加了反而要手动删。

#### 3.10.6 正文版本快照与回滚

```text
PUT /api/bookshelf/chapters/{id}            （手动保存，source=MANUAL）
POST /api/bookshelf/chapters/{id}/generate  （AI 写正文，内部传 AI_BODY）
  → 都收敛到 NovelAssetServiceImpl.updateChapter(id, req, source, allowLocked, note)
     1. 取库里当前章节，记下旧标题/旧正文/旧字数
     2. 判断内容是否真的变了（请求带 content 且与旧正文不同）
     3. 变了才 snapshot(旧内容, source)：内容为空跳过、与最近一版相同跳过
        → version_no = 最近版 + 1，随后按保留策略裁剪
     4. updateById 写入新内容（DONE 锁在校验步骤，allowLocked 仅回滚可绕过）
     5. 重算本章与全书字数

POST /api/bookshelf/chapters/{id}/versions/{versionId}/restore
  1. 校验版本属于该章（否则 40062）
  2. 以 source=RESTORE 调更新主路径：先把当前稿存一版，再把目标版写回
     → 所以「回滚」本身也可回滚

PATCH /api/bookshelf/chapters/{id}/content  （自动保存，source=AUTO，见 §3.10.11）
  → 走独立的轻量路径 saveContent：只在大改时按分钟节流写一版 AUTO 快照，不重算全书聚合
```

**为什么快照存旧内容**：当前稿只存在 `t_chapter` 一处，历史表天然是纯旧稿；
回滚就是一次普通更新，不需要「双写 + 状态标记」，也不用担心两处不一致。

**保留策略**：非 AUTO 20 版、AUTO 5 版且 7 天内（`storyforge.version.*` 可调）。
裁剪按 `version_no` 倒序计数，超出置 `deleted=1`；逻辑删行超过 100 条时用
JdbcTemplate 物理删（`@TableLogic` 会把 delete 改写成 update，绕不过去）。

#### 3.10.7 流式写正文（SSE）

```text
POST /api/bookshelf/chapters/{id}/generate/stream   Content-Type: text/event-stream
  event meta      {model, targetWords, mode, search}    检索完成、开始生成前
  event thinking  {"text":"…"}                          推理模型的思考增量（没有则不发）
  event delta     {"text":"…"}                          每个正文增量
  event done      ContentGenerateResultVO               落库 + 档案补建都完成
  event error     {code, message}                       失败
  : ping                                                每 15 秒一次注释帧，防中间层掐连接
```

**思考增量必须透传**：DeepSeek 系等推理模型先吐几十秒 `delta.reasoning_content`
（部分网关叫 `delta.reasoning`），正文 `delta.content` 才到。**只取 content 就会让前端
静默干等**——线上曾出现「首帧 76 秒才到」的问题，就是这段被丢掉了。
`OpenAiClient.readStream` 同时读这两个字段，`ChatStreamResult` 记录
`reasoning` 与 `firstReasoningMs`；`AiContentService.StreamListener.onThinking`
把它转成 `thinking` 事件，前端折叠展示在「模型思考中 / 已思考 N 字」区域。
`AiUsageService.chatStream` 的首增量重试门槛也把思考算进去（吐过思考就不再重试）。

**线程模型**：`ContentStreamService` 用独立线程池（`fixed(4)`，守护线程）跑生成，
请求线程只在建好 `SseEmitter` 后立刻返回，不占 Tomcat 工作线程。
业务逻辑依赖 `UserContextHolder` 的 ThreadLocal，因此提交任务前先捕获 `UserContext`，
线程里 `set` → finally `clear`（与 `BlueprintTaskService` 同规格）。

**为什么不在 `@PostMapping` 上写 `produces = text/event-stream`**：写了之后任何同步错误
（参数校验、404、409）在内容协商时都会要求以 `text/event-stream` 输出 JSON，全部变成
`500 No acceptable representation`。响应头由 `SseEmitter.extendResponse` 自己带即可。

**断开语义**：`send()` 失败或 `onError/onTimeout` 触发 → 置 `closed` → 下一个增量抛
`StreamAbortedException` → 上游立即关闭、**正文不落库**。已收到的文本留在前端当草稿。

**流式 vs 同步的重试差**：`AiUsageService.chatStream` **只在吐出第一个增量之前允许重试**。
一旦前端看到过字，重试会把开头重吐一遍，作者会看到重复段落——这种文本错乱比直接报错更难处理。

**降级**：上游返回 4xx、或一个增量都没给（`ChatStreamResult.empty()`），自动改走同步
`ChatResult chat(...)` 并把整段作为单个 `delta` 回给前端。若上游忽略 `stream` 直接回整段
JSON，`OpenAiClient` 也会从 `choices[0].message.content` 里取出全文，结果同样是单个 `delta`。

**脏数据容错**：空行、`:` 注释行、`event:`/`id:`/`retry:` 行一律跳过；解析失败的 JSON 行跳过且不中断整条流。

**并发保护**：`ConcurrentHashMap<chapterId, userId>`，同一章重复请求返回 `40063`（HTTP 409）；
线程池满（拒绝执行）时不算 500，返回可读的业务错误。

**前端**：EventSource 不支持自定义头，因此用 `fetch` + `ReadableStream` 手工切帧
（`generateContentStream`）；令牌刷新在 axios 拦截器之外单独兜一次。推流期间编辑区只读、
保存/取消/历史按钮让位给「停止」，state bar 显示字数进度与首字耗时。

#### 3.10.8 批量连写 N 章

```text
POST /api/bookshelf/novels/{novelId}/write-tasks     {fromChapterId|fromChapterNo, count, targetWords,
                                                      requirement, stopOnError, skipDone, useSearch}
  1. purgeExpired() 清掉 30 分钟前就结束的任务
  2. endpointResolver.resolve(BODY_GEN) 探一次端点 —— AI 没配好要在这一刻就报
  3. orderedChapters(novelId)：按 volumeNo → chapterNo 升序；一本书没章节直接 40017
  4. locateStart(...) 定位起始下标（优先 fromChapterId，其次 fromChapterNo，都没有则从第一章）
  5. runningByUser.putIfAbsent(userId, taskId) —— 撞上就 40064
  6. 候选队列 = 起始章及其之后的所有章节（运行时才逐章决定写 / 跳过）
  7. executor.submit(() -> run(task, request))，立即返回 taskId 快照

GET    /api/bookshelf/write-tasks/{taskId}   轮询：进度、当前章、逐章状态清单、累计字数
DELETE /api/bookshelf/write-tasks/{taskId}   置 cancelRequested，章与章之间退出
```

**为什么串行**：正文生成会重读全书章节，把前面几章的结尾、前情与补建的档案塞进上下文。
下一章必须读到上一章**刚写进去**的正文，否则剧情接不上——并行等于各自写各自的。
每章开写前都重新 `assetService.getChapter` 取一次，就是为了让上一章的成果可见。

**为什么不用流式**：N 条 SSE 长连接没有收益，连写的重点是「不用守着」而不是即时看字。
所以连写走 `AiContentService.generateBatch(...)`（同步路径），与单章流式共用同一套
准备与落库逻辑，只是 `source` 传 `BATCH`。

**章数语义**：`count` 是「要写几章」，不是「要覆盖几章」。`skipDone=true` 时跳过的
已定稿章节**不计入** `count`——在第 1 章（已定稿）点「连写 3 章」，实际写的是第 2~4 章。
候选章节不够时就写到最后一章为止，并在 `message` 里写明实际写了几章。

**失败与停止**：`stopOnError` 为 true 时任一章失败立即 `FAILED`；false 时记失败继续，
最终 `PARTIAL`。两种情况下 `errorMessage` 都会把失败原因按「第 N 章：原因」拼好。
停止标记只在本章写完、下一章开始之前检查——AI 请求没法安全地从半路掐断，
正在写的那章会完整落库，未开始的章标 `CANCELLED` 且不写任何东西。

**目标字数兜底**：没传 `targetWords` 时取本书最近 5 章的平均字数（钳制 300~6000），
全书还没有任何字数时兜底 2500。这样连写出来的章节长短自然接续，不会因为默认 2500
而把一本每章 800 字的书突然拉长。

**一致性**：任务只放内存（`ConcurrentHashMap` + `fixed(4)` 守护线程池，TTL 30 分钟），
进程重启即丢，与蓝图任务、拆书任务同规格——用户可以重新发起。
`Task` 的字段一律 `volatile`，`items` 用 `CopyOnWriteArrayList`，因为轮询线程与工作线程会并发读写。
只有 `userId` 相同的请求能查到任务，否则 `40021`。

#### 3.10.9 一致性 / 矛盾检查

```text
POST /api/bookshelf/novels/{novelId}/consistency/rules-check        同步，只跑规则层
  1. requireNovel(novelId) → newRunId()
  2. ruleChecker.check(全书章节 + 人物/物品/事件/章节关联/生死履历/已分析章集合)
  3. persist(...) 落 t_consistency_issue（source=RULE），返回本次 runId 的问题清单

POST   /api/bookshelf/novels/{novelId}/consistency/tasks   {scope: RECENT|CHAPTER|ALL,
                                                            chapterId, recentCount}
  1. purgeExpired() 清掉 30 分钟前就结束的任务
  2. endpointResolver.resolve(CONSISTENCY_CHECK) 探一次端点 —— AI 没配好要在这一刻就报
  3. resolveTargets(...) 选出目标章节（必须已有正文），一本都没有就 40017
  4. blocks(targets) 切成 5 章一块，最多 12 块
  5. runningByNovel.putIfAbsent(novelId, taskId) —— 撞上就 40065
  6. executor.submit(() -> run(task, ...))，立即返回 taskId 快照

GET    /api/bookshelf/consistency/tasks/{taskId}     轮询：阶段、块进度、规则/AI 条数
DELETE /api/bookshelf/consistency/tasks/{taskId}     置 cancelRequested，块与块之间退出

GET /api/bookshelf/novels/{novelId}/consistency/issues?status=&severity=&runId=   台账
GET /api/bookshelf/novels/{novelId}/consistency/runs                              批次列表
PUT /api/bookshelf/consistency/issues/{issueId}     {status: OPEN|IGNORED|FIXED}   忽略/恢复/已修复
```

**为什么分两层**：规则能判的事（死人出场、物品数量、断号、悬空关联）都是**可枚举、可验证**的，
一次查询就准，让模型去猜反而会漏报也会误报——这些做成规则层，作者打开页面就能看到，零等待零成本。
只有「正文写法与设定冲突」「伏笔没回收」「称谓前后不一」这类需要读懂语义的才交给模型，
它是付费的、慢的、不确定的，所以放在用户主动点击的异步任务里。

**为什么落库而不是每次现算**：一致性问题需要「我看过了」这个状态。作者的真实用法是——
体检一次，把误报忽略掉，把真问题改掉，下次体检只想看**新增**的。
不落库就没地方记「已忽略」，每次打开都会把同一条误报再推一遍。
所以每条问题带 `run_id`（一次检查的批次）与 `status`（`OPEN`/`IGNORED`/`FIXED`），
默认展示最近一次批次，可按批次回看。

**规则层的八条**：

| 编号 | 规则 | 类型 | 判据 | 严重度 |
|---|---|---|---|---|
| R1 | 人物状态 | `CHARACTER_STATE` | `life_status` 为死亡/失踪，却在**更晚**的章节关联里出场；死亡章取自变更履历 | `P0`；履历里查不到死亡章时降级 `P2` 并写明「无法判断是否回忆或闪回，请人工确认」 |
| R2 | 物品状态 | `ITEM_STATE` | 状态为已摧毁/遗失/消耗，却仍有数量 | `P0` |
| R2 | 物品状态 | `ITEM_STATE` | 同上，但只是仍登记在某人名下（数量已为 0） | `P1` |
| R3 | 首次登场 | `CHARACTER_STATE` | 章节关联里的出场章早于档案登记的 `first_chapter` | `P1` |
| R4 | 事件状态 | `TIMELINE` | 已废弃（`ABANDONED`）的事件仍挂在有正文的章节上 | `P1` |
| R4 | 事件状态 | `TIMELINE` | 未启用（`UNUSED`）的事件仍挂在有正文的章节上 | `P2` |
| R5a | 章号重复 | `STRUCTURE` | 同一章号被多个章节占用 | `P0` |
| R5b | 全书断号 | `STRUCTURE` | 全书章号从 1 起不连续（缺号最多列 8 个；有重复章号时跳过，交给 R5a） | `P1` |
| R5c | 排序值异常 | `STRUCTURE` | `sort_no` ≠ 卷号 × 1000 + 章号 | `P2` |
| R6 | 大纲断档 | `OUTLINE_DRIFT` | 有正文却没大纲摘要 | `P2` |
| R6 | 大纲断档 | `OUTLINE_DRIFT` | 标了已完成（`DONE`）却正文字数为 0 | `P1` |
| R7 | 档案未同步 | `ARCHIVE` | 本章有正文却没分析，而它**后面**的章节已经分析过（从后往前扫，只有断档才算） | `P1` |
| R8 | 悬空关联 | `STRUCTURE` | 章节-人物 / 章节-事件关联指向已失效（被删除）的档案，按失效 ID 去重 | `P0` |

规则一律 `clamp()` 截断（`chapterTitle` 200、`title` 120、`detail` 800、`evidence` 与 `suggestion` 400），
避免一条异常数据把插入打回、把提示词与列表撑爆。

**R5b 为什么查全书而不是「卷内从 1 连续」**：章号是**全书递增**的（新章取全书最大章号 + 1，
AI 生成大纲也一路往上加），卷只是分组。按卷判断「卷内必须从 1 连续」，
那么第一卷 1~5、第二卷 6~10 的正常分卷书会被判成「第二卷缺第 1~5 章」——分卷可管理之后
这个误报必然出现。全书断号才是这个系统里真正成立的不变量。

**AI 层怎么投喂**：一次把全书正文塞进去既超限又稀释注意力，所以按 5 章一块滚动，最多 12 块。
每块的 user 段拼装顺序：作品名与题材 → 设定摘要（每篇 300 字）→ 人物档案（姓名/身份/定位/生死/首次登场）
→ 物品档案 → 事件档案 → **前情摘要**（本块之前最多 5 章的摘要，只给摘要不给全文）
→ 本次正文（每章大纲 300 字 + 正文 6000 字）→ 输出契约。
结尾明确写上「规则层已经查过的不要重复报」，并把类型白名单写进提示词。

**去重集合必须跨块共用**：AI 按块滚动，同一条问题常被相邻两块各报一次。
`Set<String> seen` 挂在 `Task` 上贯穿整个批次（规则阶段与每一块 AI 共用），
指纹 = `source|chapterNo|issueType|title`；同步的规则速检传一个新的空集合。

**模型输出的四道闸**：① `type` 不在 `ConsistencyIssueType` 白名单里 → 丢弃；
② `STRUCTURE`/`ARCHIVE` 只允许规则层产出（模型猜结构问题不准）→ 丢弃；
③ `severity` 非法值 → 归一化到 `P2`；
④ **没有 `evidence`（依据）或没有 `title` → 丢弃**——说不清「凭什么这么说」的问题是噪音，
作者既没法核对也没法修。提示词里已经写明「给不出证据就不要报」，这里再兜一次底。
这样落库的数据永远可枚举，前端标签不会渲染出未知类型。
`chapterNo` 落在本块之外时**不丢弃**，只记章号而不挂 `chapter_id`——模型把章号偏一章是常事，
为此丢掉整条问题比定位稍偏更可惜；作者看得到章号就能自己找过去。

**失败与停止**：某一块 AI 失败只记 `failedBlocks` 并继续下一块，终态 `PARTIAL`，
规则层的 `ruleCount` 条结果一条不少；全失败时 `aiCount=0` 但规则结果仍然可读——
这是分层最大的好处：**贵的那层挂了，便宜的那层照样给答案**。
停止标记在块与块之间检查，已跑完的规则结果与已检查的块全部保留。

**一致性**：任务只放内存（`ConcurrentHashMap` + `fixed(2)`，TTL 30 分钟），与连写/蓝图/拆书同规格，
进程重启即丢。异步线程里手动 `UserContextHolder.set/clear`——数据隔离插件靠它认人，
不带上就查不到自己的数据。并发键用 `novelId` 而不是 `userId`：体检是**按书**的，
同一个人在两本书上同时体检互不干扰。

#### 3.10.10 分卷管理

```text
GET    /api/bookshelf/novels/{novelId}/volumes            卷列表（章数/字数/章号区间实时聚合）
POST   /api/bookshelf/novels/{novelId}/volumes            {title?, intro?} 卷序自动取最大 + 1
PUT    /api/bookshelf/volumes/{volumeId}                  {title?, intro?} 改名会同步该卷所有章节
DELETE /api/bookshelf/volumes/{volumeId}?moveTo={no}      有章节必须给 moveTo，否则 40068
PUT    /api/bookshelf/volumes/{volumeId}/move?direction=UP|DOWN   与相邻卷换序
PUT    /api/bookshelf/chapters/{chapterId}/volume         {volumeNo} 章节改归属，章号不变

写章节卷字段的所有链路（手动建章 / AI 大纲 / 拆书建书 / JSON 导入）先 ensureVolume(novelId, no, title)：
  卷存在 → 标题非空则顺带更新；不存在 → 建一卷
```

**为什么卷提成实体、章节还留两个冗余字段**：列表、TXT 导出、管理端目录、拆书预览全都按
`volume_no` 分组，如果去掉冗余字段，这些查询都要 JOIN 卷表并按卷序重排，改动面太大。
保留冗余的代价是「两处一致」，而这个代价被收窄到一处——`VolumeService` 是这两个字段的**唯一写入方**，
别处一律不许直接写。改名是一条 `UPDATE t_chapter SET volume_title=... WHERE volume_no=...`，
不走会存版本快照、重算字数的 `updateChapter` 主链路（改卷名不改正文，没必要）。

**换序为什么要借一个空位**：`(user_id, novel_id, volume_no)` 上有唯一索引（部分索引 `WHERE deleted = 0`），
两卷直接对调会中途撞唯一键。所以先把 A 挪到 `park = 当前最大卷号 + 1`（一定没人占），
再 B → A 原位，最后 A → B 原位；章节的 `volume_no` 用同样三步跟随，`sort_no = volume_no × 1000 + chapter_no` 一并重算。
卷序是作者理解的「第一卷 / 第二卷」，所以换的是 `volume_no` 本身，不是只换 `sort_no`。

**删除为什么强制 `moveTo`**：直接删会让那些章节挂在一个不存在的卷上——卷列表查不到、导出没有卷名行。
给了目标卷就先把章节迁过去（章号保持不变）再删卷，最后把剩余卷序重排成 1..N 连续（删卷会留洞）。
空卷则直接删。

**启动回填为什么放应用侧**：迁移只建表不回填——回填要生成雪花 ID，SQL 里造不出来（三库都得一致）。
`VolumeBackfillRunner` 在应用启动后跑，幂等：只为「有章节但卷表缺对应 (novel_id, volume_no)」的组合补记录，
卷名取该卷里第一个非空的 `volume_title`；反复启动不会重复插入。

#### 3.10.11 正文自动保存

```text
PATCH /api/bookshelf/chapters/{chapterId}/content
      body { content: string, version?: number }
      只改本章正文与字数，增量修正全书字数；version 过期返回 40071
```

**为什么不复用 `updateChapter`（PUT /chapters/{id}）**：那条主链路会重算全书字数、重建人物/事件关联、
每次都写版本快照，20 秒一次的自动保存用不起。`saveContent` 是单开的轻量路径，只做三件事：

1. 校验（已定稿 `DONE` 锁 / `version` 冲突 / 内容未变则直接返回）；
2. 按需写一条 `AUTO` 快照（内容是**保存前**的旧稿），节流由 `storyforge.version.auto-snapshot-minutes`（默认 30）控制；
3. `updateById` 更新正文与字数（带乐观锁，撞车影响 0 行即抛 `40071`），再对 `t_novel.word_count` 做一次 `+delta` 的增量 UPDATE。

**为什么不整表重算全书字数**：一本书几百章，若每次自动保存都 `SUM(word_count)` 太重；
正文变动的字数差已知（新字数 − 旧字数），一条 `SET word_count = word_count + delta` 即可，且天然并发安全。

**冲突检测为什么用 `version` 而不是 `updatedAt`**：章节实体本身带 `@Version` 乐观锁，
客户端读到的 `version` 回传即可；前端在 `version` 冲突时弹「用我的覆盖 / 放弃我的改动」——
覆盖即传 `version=null`（不做检测直接写），放弃即重新拉该章最新正文。

**前端节奏**：见 §4 的正文章节——停手 1.5s 触发、连续输入 20s 上限、单飞 + dirty 补发、
`localStorage` 按章存草稿兜底、`beforeunload` 提醒；AI 推流中与「按分析修改」弹窗打开时暂停自动保存，
AI/改稿已在服务端落库后把本地基准对齐，避免重复写。

#### 3.10.12 提示词模板导入导出

```text
GET  /api/prompt-templates/export?onlyOverridden=true|false   → 下载 JSON（Attachment）
POST /api/prompt-templates/import?mode=MERGE|SKIP_EXISTING|REPLACE  → 逐条结果
```

**包格式** `storyforge-prompt-export` v1（`PromptExportPackage`）：`format / formatVersion /
exportedAt / site / onlyOverridden / note / total / scenes[]`，每条 `PromptExportItem` 为
`scene / displayName / group / content`。导入时校验 `format` 与 `formatVersion`，不符抛 `40072`。

**导出过滤**：`onlyOverridden=true`（默认，前端复选框）只导用户改过的场景——系统默认模板随版本升级会变，
导回去没有意义；`false` 导全部可编辑场景。不可编辑场景（`40049` 那批）永不导出。

**导入逐条处理**（`importPackage`）：三种方式——
- `MERGE`（覆盖同名）：逐条 upsert；
- `SKIP_EXISTING`（只填空缺）：已存在用户覆盖的直接跳过；
- `REPLACE`（清空后导入）：先删本账号全部自定义行，再写包内容。

每条独立校验并回报 `IMPORTED / SKIPPED` 与原因：未知场景、场景不可编辑、内容为空、超长、
变量白名单不通过（复用 `PromptTemplateRenderer.unknownVariables`，点名非法变量）都会被跳过而不阻断整包。
包内 `scene` 去重（首条生效）。`normalizeMode` 把非法 mode 退回 `MERGE`。

**前端交互**（`settings/prompts/index.vue`）：导出弹窗带「只导改过的」复选框；导入弹窗**先预览后确认**——
把包内场景对照当前状态逐行标出「已改/默认」与「将要执行的动作」，统计会被跳过的条数，给出三种导入方式的单选
（选 `REPLACE` 时红色告警二次确认），确认后展示逐条结果列表，并自动选中第一个导入成功的场景。

#### 3.10.13 自动写书一轮流水线

`AutoWriteScheduler` 由 cron 触发 → `AutoWriteRunner.doRun(task)`，**一轮内严格串行**，任一步阻断即结束本轮：

```text
① 前置：读书 → 算 N（章数）与 MO（总纲目标条数 = ceil(N / 10)）
② 补总纲：现有 < MO 且未触发收尾 → 循环 MasterOutlineService.generate，单轮 ≤6 次、单次 ≤12 条
③ 补大纲：按 sort_no 找第一条「下属章节大纲 < 10 条」的总纲 → 补到 10 条（不跨总纲），单轮 ≤3 条总纲
④ 串行写正文（受 chaptersPerRun 限制）：
     生成正文 → 分析（outlineScore / aiScore）
       outlineScore < 90 → 重新生成，最多 3 版，取最高分那版落库
       aiScore < 80     → ChapterReviseService.revise → updateChapter(SOURCE_AUTO_WRITE) 覆盖本章
⑤ 每满 10 章：体检（规则层必跑，consistencyAi 时再跑 AI 深检）→ P0 > hard_issue_limit 即熔断
⑥ 收尾评估（仅 UNTIL_END 且未触发过）→ ⑦ 终止判定 / 写流水 / 清理超过 50 轮的旧流水
```

**调度实现**（`AutoWriteScheduler` + `AutoWriteSchedulingConfig`）：两个线程池——`taskScheduler`（默认 4 线程，
挂 cron）与 `autoWriteExecutor`（单任务串行执行体），不引入 Quartz。`ApplicationReadyEvent` 时从库载入
`enabled=1` 的任务并注册 `CronTrigger`；任务增删改 / 启停即时注销再注册；启动时把残留 `RUNNING` 重置为 `IDLE`
（进程重启视为中断）。每个任务一个在跑标记，上一轮未结束时本轮记 `SKIPPED`。定时线程内必须
`UserContextHolder.set(...)` / `clear()`。

**只读锁**（`AutoWriteGuard`）：判定口径为「任务 `enabled=1` 且 `status ∈ {IDLE, RUNNING}`」——即从配置启用那一刻起
就锁，而不是等真正在写。`assertEditable(novelId)` 命中即抛 `40073`；流水线自身写库用 `guard.bypass(...)`
（ThreadLocal 放行）穿过。写入口逐个挂载：基本信息、设定、章节、大纲、总纲、人物/关系/属性/背包、势力、物品、
事件、卷、AI 生成（正文 / 大纲 / 总纲）、分析、改稿、导入、拆书保存。查询、导出、体检列表不拦。

**失败与熔断**：单次 AI 调用失败原地重试 2 次（`AI_RETRY_TIMES`）；仍失败则本轮 `FAILED`（已写章节保留），
下周期继续；连续 3 个周期失败由 `AutoWriteScheduler.afterRun` 累加 `consecutive_failures` 并转 `PAUSED`。

## 7. 多数据库设计

### 7.1 三处收敛

| 层 | 方案 |
|---|---|
| DDL | `db/migration/{postgresql,mysql,sqlite}/V1__baseline.sql`；MySQL/SQLite 由 `script/db/gen-baseline.mjs` 从 PostgreSQL 版派生，`--check` 校验同步 |
| DML | 不写方言；大小写不敏感用 `LOWER(col) LIKE LOWER(CONCAT('%', #{kw}, '%'))`；时间运算在 Java 侧算；取日期部分用 `<sql id="dateOf">` 按 `_databaseId` 分支 |
| 运行时 | `DbDialect` / `DbDialectProvider` 版本校验；`DatabaseDialectConfig` 提供 `_databaseId`；`SqliteLocalDateTimeTypeHandler` 处理 TEXT 时间 |

### 7.2 已知限制

| 限制 | 说明 |
|---|---|
| MySQL 部分索引 | 不支持 `WHERE`，唯一性用条件函数列等价实现，要求 8.0.13+ |
| SQLite 并发 | 单写者；连接池压到 4、`busy_timeout=10s`；不适合多用户并发写 |
| SQLite 时间精度 | TEXT 存储毫秒；PostgreSQL 为微秒，跨库迁移以毫秒为准 |
| SQLite 时钟 | `CURRENT_TIMESTAMP` 为 UTC，故当前时间一律应用侧写入 |
| 自动写书单实例 | cron 注册在进程内存，多实例部署会出现重复触发；当前只支持单实例（线上容器即单实例），不做分布式抢占 |

## 8. 部署设计

### 8.1 容器

```text
remote/Dockerfile（运行镜像）
  FROM eclipse-temurin:17-jre
  COPY app.jar /app/app.jar
  ENV SERVER_PORT=8080 JAVA_OPTS="-Xms128m -Xmx640m"
  HEALTHCHECK curl -f http://127.0.0.1:${SERVER_PORT}/actuator/health
  ENTRYPOINT ["/app/start.sh"]
```

- `remote/docker-compose.yml`：`app`（`image: ${APP_IMAGE:-ccr.ccs.tencentyun.com/jiaqiong/story-forge:v1.0.0}`，**无 `build:` 段**）+ `postgres:16-alpine`，卷挂载 `./data/{pg,files,covers,logs}`。
- `remote/docker-compose.build.yml`：仅在 `--from-source` 时叠加，为 `app` 补 `build:`（上下文三件：`app.jar` / `Dockerfile` / `start.sh`）。
- `.env` 只在首次部署生成（JWT 密钥、加密主密钥、DB 口令、初始 admin 口令），再次部署不覆盖（主密钥变更会导致已存密文无法解密）。

### 8.2 镜像与网关

- `script/deploy/build.sh`：本地打 jar → 组装上下文（jar + Dockerfile + start.sh）→ 上传 `/opt/storyforge/image-build/` → 服务器 `docker build` → **skopeo copy** 推送 TCR（`docker push` 推大层会超时，仅作兜底）。
- `script/deploy/deploy.sh`（默认）：只上传 `docker-compose.yml` → 远端 `compose pull app` + `up -d --no-build`，部署链路不涉及编译。`--from-source` 才回到源码构建（叠加 `docker-compose.build.yml` 后 `up -d --build`）。
- Nginx（模板 `script/deploy/remote/nginx-storyforge.conf`）：80 → 301；443 反代 8080；`proxy_buffering off`、`proxy_read_timeout 300s`、`client_max_body_size 50m`；不开启 HSTS。

### 8.3 桌面版

`com.storyforge.desktop`：

- `AppHome`：数据目录按优先级解析——`-Dstoryforge.home=<目录>` 显式指定 > `-Dstoryforge.storage=user`
  （安装版，取 `%APPDATA%\StoryForge\data`）> 由 `jpackage.app-path` 推导 exe 同级 `data/`（绿色版）；
  同时把 `org.sqlite.tmpdir` 与 `java.io.tmpdir` 指到 `data/tmp`。
  安装版之所以不用 `%LOCALAPPDATA%`：jpackage 的 per-user 安装目录就是 `%LOCALAPPDATA%\StoryForge`，
  数据放同处会被卸载程序一并删除。
- `PortPicker`：从 8080 起探测可用端口（至 8089）。
- `InstanceLock`：`data/.instance.lock` 排他锁；端口另存 `.instance.port`（Windows 文件锁连读都拒）。
- `DesktopBootstrap`：仅当存在 `jpackage.app-path` 或 profile 含 `sqlite` 时接管端口、锁与浏览器打开；PG/MySQL 服务器模式不介入。

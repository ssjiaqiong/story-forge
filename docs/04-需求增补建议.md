# 04-需求增补建议（候选池）

> 本文不是承诺排期，而是一份**缺口盘点**：对照 [01-需求规格说明书](./01-需求规格说明书.md) 已实现的 175 条 FR、[02-详细设计](./02-详细设计说明书.md) 的 33 张表与当前前端 10 个路由，找出「用户会用但系统还没有」的地方，按价值与成本排序。
>
> 盘点时间：2026-10-26。**已实现的功能不在此列**（例如拆书、智能助手、按分析修改、封面、导入导出 JSON、建书追问均已上线）。

## 0. 一句话结论

功能面已经很完整，缺的几乎都集中在**「写完之后」**：稿子救不回来（无版本历史）、交不出去（只有 JSON 导出）、删了找不回（无回收站）。这三件事成本都不高，却决定了一个作者敢不敢把整本书托付给它。

---

## 1. P0：把创作闭环补上（建议优先）

### 1.1 章节正文版本历史与回滚

| 项 | 内容 |
|---|---|
| 建议编号 | `FR-NOVEL-75` |
| 现状 | 保存即覆盖（`FR-NOVEL-14`）；「按分析修改」保存后直接改写正文（`FR-NOVEL-55`）。33 张表里没有版本表。只有分析报告和变更履历，**正文本身没有快照** |
| 痛点 | AI 改稿不满意只能自己重写；误删段落、误覆盖无法撤销。长篇作者最怕的不是写不出，而是丢稿 |
| 做法 | 新表 `t_chapter_version`（`novel_id`/`chapter_id`/`version_no`/`content`/`word_count`/`source`(MANUAL/AI_GEN/REVISE)/`created_at`）。保存、AI 生成、按分析修改三条路径各留一版，每章保留最近 20 版（超出删最旧）。接口 `GET /api/chapters/{id}/versions`、`GET .../versions/{no}`、`POST .../rollback`。前端抽屉做版本列表 + 对比，diff 算法复用 `ChapterReviseDialog` 已有的段落级对齐 |
| 成本 | 中（后端 1~2 天，前端对比视图 1~2 天） |
| 验收 | 连续保存两次可回滚到上一版；AI 改稿保存后原稿能在版本列表里找回；回滚本身也产生一版，可再回滚 |

### 1.2 导出为 TXT / DOCX

| 项 | 内容 |
|---|---|
| 建议编号 | `FR-NOVEL-76` |
| 现状 | 只有 `FR-NOVEL-62` 的 JSON 包——那是**备份格式**，给机器读的，章节正文散在数组里还带 ID |
| 痛点 | 作者写完要投稿、要发平台，需要的是「书名 + 作者 + 简介 + 第 1 章…第 N 章」的可读文档。现在只能自己从页面复制 |
| 做法 | `GET /api/bookshelf/novels/{id}/export.txt`（参数 `scope=all\|done`、`withSynopsis=true`），服务端按卷、章号排序拼接，输出 UTF-8 with BOM（Windows 记事本不乱码）。DOCX 走 POI：书名一页、简介页、每章另起一页、章标题用 Heading 1 |
| 成本 | 小（TXT 半天，DOCX 1 天） |
| 验收 | 导出的 TXT 能直接被常见网文平台识别章节；DOCX 章标题可生成目录；中文与空行正常 |

### 1.3 回收站（小说 / 章节恢复）

| 项 | 内容 |
|---|---|
| 建议编号 | `FR-NOVEL-77` |
| 现状 | 删除是逻辑删（`FR-NOVEL-04`），数据还在库里，但**没有任何恢复入口**；`FR-ADMIN-04` 的物理清除只对超管开放。普通用户误删只能找超管，而超管能做的只有「彻底删掉」 |
| 痛点 | 「30 天可恢复」目前是空话，用户视角就是永久删除 |
| 做法 | 书架加「回收站」视图（`GET /api/novels?deleted=1`）；`POST /api/bookshelf/novels/{id}/restore` 恢复本体与全部关联（关联行本就跟着 `novel_id`）；重名自动加序号；显示剩余保留天数。章节同理：正文列表加「已删除章节」折叠区 |
| 成本 | 小（1 天） |
| 验收 | 删书 → 回收站可见 → 恢复后设定、人物、章节、事件、封面全在；恢复后书架排序正确 |

## 2. P1：体验与效率

### 2.1 流式输出（SSE）

| 项 | 内容 |
|---|---|
| 建议编号 | `FR-NOVEL-78` |
| 现状 | `NFR-24` 明确写着「不使用流式响应」。一次 2500 字正文要等 60~120 秒，界面只有进度条和阶段文案 |
| 痛点 | 等待期间无法判断是卡死还是在写；想提前读到一半不满意就中断，现在做不到 |
| 做法 | Spring MVC 用 `SseEmitter`（不引 WebFlux）；`AiUsageService` 增流式分支，token 用量优先取最后一个 chunk 的 `usage`，取不到按字数估算并标记 `estimated=true`；前端用 `fetch` + `ReadableStream` 逐字追加，支持「停止生成」（中断后已生成部分保留为草稿）。**只对正文/大纲这类自由文本开启**，蓝图四段、分析、拆书等要解析 JSON 的场景保持非流式 |
| 成本 | 大（后端 2~3 天，前端 2 天，还要回归 token 统计与错误码） |
| 注意 | Nginx 模板已配 `proxy_buffering off`，网关侧不用改 |
| 验收 | 首字 3 秒内到达；停止生成后已写内容不丢；token 统计与改造前误差 < 10% |

### 2.2 批量连写 N 章

| 项 | 内容 |
|---|---|
| 建议编号 | `FR-NOVEL-79` |
| 现状 | `FR-NOVEL-15` 一次一章，每章都要点一次、等一次。想存稿 10 章得守着点 10 次 |
| 做法 | 复用拆书/蓝图的「内存任务 + 轮询」模式（`DeconstructTaskService` 已有现成骨架）；按大纲顺序连写（默认 3，上限 10），每章完成即更新状态与字数，中途失败可从下一章续；每章之间把上一章结尾带入（现有逻辑天然支持） |
| 成本 | 中（2~3 天） |
| 验收 | 连写 5 章后字数统计正确；中途取消不影响已完成章节；单章失败不阻断后续 |

### 2.3 一致性 / 矛盾检查

| 项 | 内容 |
|---|---|
| 建议编号 | `FR-NOVEL-80` |
| 现状 | 分析只做三件事：字数核对、大纲贴合评分、AI 率（`FR-NOVEL-48~50`），加上本章事件收尾（`FR-NOVEL-47`）。**没有跨章矛盾检测** |
| 痛点 | 长篇最常见的翻车：人物已经写死了后面又出场、物品已经毁了又拿出来用、时间线倒流、身份前后不一致。作者自己很难查 |
| 做法 | 两层。规则层（零成本、必做）：人物 `life_status=DEAD` 却在更晚章节出场、背包条目 `LOST/CONSUMED` 之后又被使用、事件时间早于已有事件。AI 层：把近 5 章摘要 + 关键人物当前状态交给模型，问「有无硬矛盾」，要求指出章号与依据。结果作为分析报告的新分区「一致性问题」，可勾选进「按分析修改」 |
| 成本 | 中（2~3 天） |
| 验收 | 造一个「第 3 章写死、第 5 章出场」的样本能报出来；无误报干扰正常章节 |

### 2.4 写作目标与热力图

| 项 | 内容 |
|---|---|
| 建议编号 | `FR-DASH-09` |
| 现状 | 仪表盘有近 14 天趋势（`FR-DASH-06`），但没有目标、没有连续性统计 |
| 做法 | 用户偏好表加 `daily_goal_words`；仪表盘顶部加今日进度环、连续写作天数、GitHub 风格年度热力图（按 `t_chapter.updated_at` 的日字数聚合） |
| 成本 | 小（1 天，纯查询与前端） |
| 验收 | 今日写 1200 字 / 目标 2000 时进度环 60%；断更当天热力图留空、连续天数归零 |

### 2.5 卷的独立管理

| 项 | 内容 |
|---|---|
| 建议编号 | `FR-NOVEL-81` |
| 现状 | 卷只是章节上的两个字段（`volumeNo`/`volumeTitle`），没有卷实体。改卷名要逐章改 |
| 做法 | 新增 `t_volume`（`novel_id`/`volume_no`/`title`/`sort_no`），章节保留 `volume_no` 做关联；大纲页加卷级操作：新建卷、重命名（批量写回章节）、调整章节归属顺序 |
| 成本 | 小~中（2 天，含迁移） |
| 验收 | 改一次卷名，该卷下所有章节标题同步变；前后端都不出现空卷 |

### 2.6 正文自动保存

| 项 | 内容 |
|---|---|
| 建议编号 | `FR-NOVEL-82` |
| 现状 | 只有手动保存，刷新、崩溃、切章都不留底 |
| 做法 | 前端每 30 秒把编辑中内容写 `localStorage`（键含 `chapterId` + `updatedAt`）；再次进入该章时提示「有未保存草稿，是否恢复」；切章前若有未保存改动先弹确认 |
| 成本 | 小（半天） |
| 验收 | 编辑中强退再进，能恢复到最后一次自动保存；已保存内容不被旧草稿覆盖 |

## 4. 明确不建议做（写清理由，避免反复讨论）

| 方向 | 为什么不建议 |
|---|---|
| 多实例 / 集群部署 | `NFR-04` 定位是单实例、个人与小规模用户；限流是进程内令牌桶，要多实例就得引 Redis，与 `NFR-15`「无外部中间件」直接冲突 |
| 多人协作编辑（实时/CRDT） | 与 `FR-USER-01`「用户即空间」的数据模型冲突，改动面覆盖权限、锁、冲突合并，收益对单人写作产品很低 |
| 对象存储（OSS/S3） | `NFR-28` 明确本地卷挂载；封面与 data 目录已经有备份路径，换存储只增加运维成本 |
| 全文检索 / ES | 数据量级（单用户 50 本 / 2000 万汉字）用 `LIKE` + 索引足够，`NFR-15` 也不允许引 ES |

## 5. 如果只做三件事

1. **版本历史**（1.1）——它决定「敢不敢让 AI 动我的稿」
2. **TXT/DOCX 导出**（1.2）——它决定「写完了能不能交出去」
3. **回收站**（1.3）——它决定「手滑一次会不会没命」

三条加起来约 4~5 个工作日，全部属于「不可逆损失」类修复，做完之后产品才算真正能承载一本长篇。

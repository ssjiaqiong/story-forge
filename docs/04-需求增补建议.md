# 04-需求增补建议（候选池）

> 本文不是承诺排期，而是一份**缺口盘点**：对照 [01-需求规格说明书](./01-需求规格说明书.md) 的已实现条目、[02-详细设计](./02-详细设计说明书.md) 的表结构与当前前端路由，找出「用户会用但系统还没有」的地方，按价值与成本排序。
>
> 盘点时间：2026-10-26。**已实现的功能不在此列**（拆书、智能助手、按分析修改、封面、导入导出 JSON、建书追问、TXT 导出、章节正文版本历史、流式输出、批量连写 N 章均已上线）。
>
> 条目里的「建议编号」只是占位：真正的 FR 编号在落地时由 01 统一分配，可能与占位号不同。

## 0. 一句话结论

功能面已经很完整，缺的几乎都集中在**「写完之后」**：删了找不回（无回收站）、排版交不出去（只有 JSON 备份与 TXT 纯文本，没有 DOCX）。这几件事成本都不高，却决定了一个作者敢不敢把整本书托付给它。

## 1. P0：把创作闭环补上（建议优先）

### 1.1 导出为 DOCX（排版稿）

| 项 | 内容 |
|---|---|
| 建议编号 | `FR-NOVEL-76` |
| 现状 | 已有 JSON 备份（`FR-NOVEL-62`）与 TXT 成品（`FR-NOVEL-75`）。TXT 只有纯文字，投稿到要求 Word 的平台得自己再排一遍 |
| 痛点 | 部分平台/编辑只要 Word；作者要交「书名页 + 章节标题层级 + 分页」的排版稿，纯文本做不到 |
| 做法 | `GET /api/bookshelf/novels/{id}/export/docx`，用 POI 生成：书名页（书名/笔名/简介）→ 每章另起一页 → 章标题用 Heading 1（Word 里可直接生成目录）。范围与开关复用 TXT 的 `TxtExportOptions` |
| 成本 | 小（1 天，只多一个 POI 写文档的类） |
| 验收 | Word 打开目录可自动生成；每章从新页开始；中文不乱码；章标题层级正确 |

### 1.2 回收站（小说 / 章节恢复）

| 项 | 内容 |
|---|---|
| 建议编号 | `FR-NOVEL-77` |
| 现状 | 删除是逻辑删（`FR-NOVEL-04`），数据还在库里，但**没有任何恢复入口**；`FR-ADMIN-04` 的物理清除只对超管开放。普通用户误删只能找超管，而超管能做的只有「彻底删掉」 |
| 痛点 | 「30 天可恢复」目前是空话，用户视角就是永久删除 |
| 做法 | 书架加「回收站」视图（`GET /api/novels?deleted=1`）；`POST /api/bookshelf/novels/{id}/restore` 恢复本体与全部关联（关联行本就跟着 `novel_id`）；重名自动加序号；显示剩余保留天数。章节同理：正文列表加「已删除章节」折叠区 |
| 成本 | 小（1 天） |
| 验收 | 删书 → 回收站可见 → 恢复后设定、人物、章节、事件、封面全在；恢复后书架排序正确 |

## 2. P1：体验与效率

### 2.1 ~~流式输出（SSE）~~ ✅ 已实现（v1.0.2 开发中）

> 已落地并迁入 `docs/01` 的 `FR-NOVEL-91~96`、`docs/02` 的 §3.10.7，
> `NFR-24` 同步改为「正文场景支持流式响应」。

| 项 | 落地情况 |
|---|---|
| 实现范围 | 只对正文开放 SSE（`POST /chapters/{id}/generate/stream`）；大纲、蓝图四段、分析、拆书这些要解析 JSON 的场景保持非流式，与当初的建议一致 |
| 与建议的差异 | ① token 用量不「估算」——上游给了 `usage` 就记，没给就按 0 落库（成功/失败、耗时才是稳态口径），没引入 `estimated` 字段；② 停止后并非「保留为草稿」到库里，而是**完全不落库**，只在前端编辑区留着，作者确认后再保存 |
| 验收结果 | `content-stream-e2e.py` 50 项断言全绿：事件序列、增量分批到达、脏帧容错、中止不落库且断上游、降级与整包回、并发 `40063`、长流 37 秒不被异步超时截断、旧同步接口回归正常 |

### 2.2 ~~批量连写 N 章~~ ✅ 已实现（v1.0.2 开发中）

> 已落地并迁入 `docs/01` 的 `FR-NOVEL-97~103`、`docs/02` 的 §3.10.8。

| 项 | 落地情况 |
|---|---|
| 实现范围 | 一次发起写 1~10 章（前端默认 3），串行执行；可指定起始章、每章目标字数与统一附加要求；可停止、可设置失败后是否继续 |
| 与建议的差异 | ① 章数语义更严：`count` 指「要写几章」，跳过已定稿的章节**不计入** count，所以「连写 3 章」不会浪费在已写完的章上；② 目标字数不写死默认 2500，而是取本书最近 5 章的平均字数（钳制 300~6000），让章节长短自然接续；③ 不做「中途失败从下一章续」的独立入口，而是用 `stopOnError` 开关在一次任务里表达（true 立即停 / false 跳过失败章继续，最终 PARTIAL） |
| 验收结果 | `write-task-e2e.py` 67 项断言全绿：连写 3 章（跳过 1 章定稿）成功 3 / 跳过 1 / 失败 0；第 3 章提示词里能看到第 2 章刚写的正文（上下文接续）；`stopOnError` 两种取值分别得到 FAILED 与 PARTIAL；停止后未开始章无正文、已写章保留；同用户并发 40064；参数/起始章/任务不存在分别 10001 / 40017 / 40021；`BATCH` 版本与用量统计正确 |

### 2.3 一致性 / 矛盾检查

| 项 | 内容 |
|---|---|
| 建议编号 | `FR-NOVEL-80` |
| 现状 | 分析只做三件事：字数核对、大纲贴合评分、AI 率（`FR-NOVEL-48~50`），加上本章事件收尾（`FR-NOVEL-47`）。**没有跨章矛盾检测** |
| 痛点 | 长篇最常见的翻车：人物已经写死了后面又出场、物品已经毁了又拿出来用、时间线倒流、身份前后不一致。作者自己很难查 |
| 做法 | 两层。规则层（零成本、必做）：人物 `life_status=DEAD` 却在更晚章节出场、背包条目 `LOST/CONSUMED` 之后又被使用、事件时间早于已有事件。AI 层：把近 5 章摘要 + 关键人物当前状态交给模型，问「有无硬矛盾」，要求指出章号与依据。结果作为分析报告的新分区「一致性问题」，可勾选进「按分析修改」 |
| 成本 | 中（2~3 天） |
| 验收 | 造一个「第 3 章写死、第 5 章出场」的样本能报出来；无误报干扰正常章节 |

### 2.4 写作目标与热力图

| 项 | 内容 |
|---|---|
| 建议编号 | `FR-DASH-09` |
| 现状 | 仪表盘有近 14 天趋势（`FR-DASH-06`），但没有目标、没有连续性统计 |
| 做法 | 用户偏好表加 `daily_goal_words`；仪表盘顶部加今日进度环、连续写作天数、GitHub 风格年度热力图（按 `t_chapter.updated_at` 的日字数聚合） |
| 成本 | 小（1 天，纯查询与前端） |
| 验收 | 今日写 1200 字 / 目标 2000 时进度环 60%；断更当天热力图留空、连续天数归零 |

### 2.5 卷的独立管理

| 项 | 内容 |
|---|---|
| 建议编号 | `FR-NOVEL-81` |
| 现状 | 卷只是章节上的两个字段（`volumeNo`/`volumeTitle`），没有卷实体。改卷名要逐章改 |
| 做法 | 新增 `t_volume`（`novel_id`/`volume_no`/`title`/`sort_no`），章节保留 `volume_no` 做关联；大纲页加卷级操作：新建卷、重命名（批量写回章节）、调整章节归属顺序 |
| 成本 | 小~中（2 天，含迁移） |
| 验收 | 改一次卷名，该卷下所有章节标题同步变；前后端都不出现空卷 |

### 2.6 正文自动保存

| 项 | 内容 |
|---|---|
| 建议编号 | `FR-NOVEL-82` |
| 现状 | 只有手动保存，刷新、崩溃、切章都不留底 |
| 做法 | 前端每 30 秒把编辑中内容写 `localStorage`（键含 `chapterId` + `updatedAt`）；再次进入该章时提示「有未保存草稿，是否恢复」；切章前若有未保存改动先弹确认 |
| 成本 | 小（半天） |
| 验收 | 编辑中强退再进，能恢复到最后一次自动保存；已保存内容不被旧草稿覆盖 |

## 4. 明确不建议做（写清理由，避免反复讨论）

| 方向 | 为什么不建议 |
|---|---|
| 多实例 / 集群部署 | `NFR-04` 定位是单实例、个人与小规模用户；限流是进程内令牌桶，要多实例就得引 Redis，与 `NFR-15`「无外部中间件」直接冲突 |
| 多人协作编辑（实时/CRDT） | 与 `FR-USER-01`「用户即空间」的数据模型冲突，改动面覆盖权限、锁、冲突合并，收益对单人写作产品很低 |
| 对象存储（OSS/S3） | `NFR-28` 明确本地卷挂载；封面与 data 目录已经有备份路径，换存储只增加运维成本 |
| 全文检索 / ES | 数据量级（单用户 50 本 / 2000 万汉字）用 `LIKE` + 索引足够，`NFR-15` 也不允许引 ES |

## 5. 如果只做三件事

1. **回收站**（1.2）——它决定「手滑一次会不会没命」
2. **DOCX 导出**（1.1）——它决定「写完了能不能交给只要 Word 的编辑」
3. **正文自动保存**（2.6）——它决定「写一下午会不会因为断电丢光」

版本历史与 TXT 导出已经落地；剩下的三条里前两条属于「不可逆损失」类修复，第三条属于日常写作的兜底。
